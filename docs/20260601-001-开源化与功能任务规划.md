# QTP 开源化与功能任务规划

> 文档定位：GitHub 开源项目整理清单 / 功能路线拆解 / 后续验收与 PR 合并依据
> 输入来源：`README.md`、`ROADMAP.md`、`docs/20260529-*`、`QTP_AI应用回归测试平台_详细需求规格说明书.md`
> 当前策略：先把北极星链路打磨成可信演示，再扩展开源采纳能力。

## 1. 目标

本轮开源化工作的目标不是把 QTP 包装成“模块很多”的后台系统，而是让外部开发者在 GitHub 上快速理解三件事：

1. QTP 解决什么独特问题：AI 应用改版后的多轮回归退化识别。
2. 如何在本地 5 分钟内跑出北极星演示：基线 vs 候选、失败诊断、证据链。
3. 如何参与建设：看路线图、提 Issue、提交 PR、通过 CI 验收。

## 3. 功能规划原则

QTP 的功能建设按“可信演示优先”排序：

1. **P0：开源信任基础**  
   README、治理文档、CI、任务拆解、可复现启动说明必须先稳定。没有这些，外部开发者无法判断项目是否认真。

2. **P1：北极星链路硬化**  
   继续围绕执行对比与失败诊断，保证 seed 数据、页面、查询、文案、验收脚本能稳定展示“第 3 轮使用旧值 80”的退化证据。

3. **P2：最窄闭环补齐**  
   应用接入、HTTP JSON Adapter、多轮 Golden Case、回归套件、执行任务、对比任务要形成一条真实可操作链路。

4. **P3：可信退化判定**  
   引入多次采样、稳定性评分、REVIEW 状态和置信度阈值，避免把随机抖动误判为真实失败。

5. **P4：多轮上下文追踪**  
   实现上下文变量抽取、跨轮更新追踪、`mustUpdateContext` 与 `mustNotUseStaleContext` 断言。

6. **P5：资产飞轮入口**  
   会话录制、一键转 Golden Case、复核结果沉淀回归套件。

7. **P6：开源采纳增强**  
   Docker 一键启动、演示录屏/GIF、CLI/CI 集成、更多 Adapter、示例项目。

## 4. 任务拆解

### Task 1：开源门面与治理文档

**范围**
- README 补齐治理入口和开发者命令。
- 新增贡献、安全、支持、行为准则。
- 新增 Issue/PR 模板。

**交付物**
- `README.md`
- `CONTRIBUTING.md`
- `CODE_OF_CONDUCT.md`
- `SECURITY.md`
- `SUPPORT.md`
- `.github/ISSUE_TEMPLATE/bug_report.yml`
- `.github/ISSUE_TEMPLATE/feature_request.yml`
- `.github/pull_request_template.md`

**验收**
- GitHub 首页能看到定位、启动、路线、贡献、许可证。
- 新贡献者能按 `CONTRIBUTING.md` 跑 `pnpm setup`、`pnpm typecheck`、`pnpm test`、`pnpm build`。
- Issue 与 PR 模板能收集复现、动机、验收和截图信息。

### Task 2：CI 与工程命令对齐

**范围**
- 修正 GitHub Actions 中过期的脚本名。
- CI 使用根目录现有脚本，避免开源贡献者第一次 PR 就被错误 CI 阻塞。

**交付物**
- `.github/workflows/ci.yml`

**验收**
- CI 步骤包含 install、typecheck、test、build。
- 不再引用当前 `package.json` 中不存在的 `check:topology` 或 `build:web`。

### Task 3：功能路线转成可执行 Backlog

**范围**
- 从详细需求规格说明书、README、ROADMAP 中抽取任务。
- 按 P0-P6 排序，给出每个任务的验收口径。

**交付物**
- 本文档的任务拆解章节。
- `docs/superpowers/plans/2026-06-01-open-source-readiness.md`

**验收**
- 每个优先级阶段都有可验证产物。
- 每个任务能直接转成 GitHub Issue。
- 验收标准覆盖文档、功能、测试和 PR 合并路径。

### Task 4：北极星链路验收

**范围**
- 验证 `pnpm setup` 后 seed 数据可用。
- 验证执行对比页和失败诊断页能打开并展示北极星故事。

**建议命令**

```bash
pnpm setup
pnpm typecheck
pnpm test
pnpm build
pnpm dev
```

**浏览器验收**
- 打开 `http://127.0.0.1:3000/ai-quality-platform`。
- 进入回归对比页，确认候选版本有新增失败。
- 点击诊断，确认第 3 轮的旧值 `80` 与新值 `20` 被高亮说明。

### Task 5：后续功能实现顺序

| 优先级 | 功能 | 主要文件区域 | 验收标准 |
|---|---|---|---|
| P1 | 北极星 seed 与页面稳定性 | `packages/shared-database`、`apps/web/src/features/comparison`、`apps/web/src/features/diagnosis` | seed 后两屏稳定展示，测试覆盖核心文案与状态 |
| P2 | HTTP JSON Adapter 最窄接入 | `packages/ai-adapter`、应用接入页面 | 能配置 URL、Header、请求模板、响应 JSONPath，并完成调试 |
| P2 | 多轮 Golden Case 管理 | `packages/shared-database`、用例资产页面 | 能编辑多轮输入、断言和风险等级 |
| P2 | 回归套件与执行任务 | `packages/eval-engine`、套件/执行页面 | 能选择用例执行并落库结果 |
| P3 | 稳定性评分 | `packages/eval-engine` | 多次采样后输出真退化/疑似抖动/REVIEW |
| P4 | 上下文断言 | `packages/eval-engine`、诊断页面 | 能识别旧值引用并给证据链 |
| P5 | 会话录制转用例 | 会话录制页面、用例生成服务 | 多轮会话可保存并生成 Golden Case 草稿 |
| P6 | 开源采纳增强 | Docker、CLI、演示资产 | 一键启动、录屏/GIF、CI 示例可用 |

## 5. PR 与合并策略

1. 所有变更从 `codex/*` 或当前功能分支发起 PR。
2. PR 必须说明：改了什么、为什么改、如何验收、是否影响 README/ROADMAP/CHANGELOG。
3. 合并前至少完成：
   - `pnpm typecheck`
   - `pnpm test`
   - `pnpm build`
4. 涉及 UI 的 PR 必须附浏览器截图或录屏。
5. 涉及数据库 schema 或 seed 的 PR 必须说明迁移/重建方式。

## 6. 当前结论

当前仓库已经具备开源化基础：Apache-2.0、README、ROADMAP、北极星两屏和单体启动脚本都已存在。本轮重点是补齐 GitHub 项目治理资料、修正 CI、把功能规划转成可执行任务，让后续“实现 -> 验收 -> PR -> 合并主干”有清晰依据。
