# 切片重建架构决策（ADR）

> 文档定位：北极星切片"全新重搭"的架构决策记录 / 重建依据
> 背景：用户确认现有实现可整体删除，按北极星切片（多轮回归 + 失败诊断）窄而深重建，沿用设计稿视觉规范。
> 配套：[ROADMAP.md](../ROADMAP.md) · [失败诊断与执行对比设计规格](./20260529-003-失败诊断与执行对比设计规格.md)

## 待决：要不要收敛现有架构

### 现状
现有为 monorepo 下 **4 个 NestJS 运行单元**（quality-gateway + platform/execution/ai-invocation 三服务）+ **MySQL** + Next.js 前端。这套"服务边界前置"来自原"广而浅"大平台设想（原设计文档原则 6）。

### 矛盾
我们已把产品收敛到一条窄垂直链路。对一个早期开源项目，4 服务 + 必须装 MySQL 带来两个问题：
1. **上手成本高**：贡献者要起 4 个进程 + Docker MySQL 才能跑起来，违背"5 分钟跑通"的开源采纳前提。
2. **维护面大**：跨服务转发、契约、健康探针等大量代码服务于尚不存在的规模。

### 决策（建议）
重建为**单体 + 零依赖本地启动**：

| 维度 | 现状 | 重建后 |
|---|---|---|
| 后端 | gateway + 3 NestJS 服务 | **单个后端**（Next.js Route Handlers 或单 NestJS app） |
| 数据库 | MySQL（必须 Docker） | **Prisma + SQLite 默认**（零依赖），MySQL 作为可选 provider |
| 本地启动 | 多进程 + Docker | **`pnpm install && pnpm db:push && pnpm seed && pnpm dev`** |
| 前端 | Next.js + Radix + Tailwind v4 | **沿用**（含 components/ui、app-shell、登录） |
| 设计语言 | 设计稿视觉规范 | **沿用** |

### 沿用 / 重建 / 丢弃

- **沿用**：前端工程脚手架、`components/ui/*` 设计系统、布局与主题、登录页；pnpm/monorepo/TS 配置。
- **重建**：领域数据模型（按 003 规格的版本/多轮/对比/诊断）、后端 API、功能页面（执行对比、失败诊断）。
- **丢弃**：gateway 跨服务转发层、三服务拆分、MySQL 强依赖、广而浅的单次评估管线代码。

### 不选"叠加"的理由
在 4 服务 + MySQL 上叠加版本对比/诊断，会把"窄而深"的新能力埋进"广而浅"的旧骨架，启动成本和维护面都继续放大，与开源采纳目标背离。

### 风险与回退
- 全程在分支 `docs/open-source-positioning` 进行，旧实现保留在 git 历史，**随时可回退**。
- 若未来确需服务化（规模上来），Prisma 可切 MySQL、后端可再拆，单体不构成不可逆锁定。

### 可被否决点（linchpin）
**收敛为单体 + SQLite 默认** 是本次重建唯一的高影响决策。若团队坚持保留 NestJS 多服务形态，则改为"单 NestJS app + Prisma(MySQL/SQLite)"，其余结论不变。

## 重建执行顺序（确认后）
1. 收敛工程结构（删旧服务/网关，保留前端壳与 UI）。
2. 新 Prisma schema（SQLite）：App / AppVersion / Case(多轮) / Run / Result(逐轮+断言) / Diagnosis / Comparison。
3. `seed`：写入北极星样本（同一多轮用例，基线通过 / 候选第 3 轮用旧值退化）。
4. 后端 API：对比查询、诊断查询。
5. 前端：执行对比页 + 失败诊断页（按 003 规格）。
6. 一键启动文档 + 演示路径。
