# QTP 产品定位与路线规划

> 文档定位：战略输入 / 定位依据 / 路线决策记录
> 配套文档：[ROADMAP.md](../ROADMAP.md)（执行层分阶段计划）、[README.md](../README.md)（对外叙事）

本文记录 QTP 从"一个看起来够不上开源水平的系统"收敛到"窄而深、有明确护城河的开源项目"的思考过程与决策结论，作为后续所有功能取舍的依据。

---

## 1. 问题诊断：不是功能不够，是没有"非选你不可的理由"

LLM 评估赛道极度拥挤，且对手都是明星开源项目（promptfoo、DeepEval、Ragas、Langfuse、Phoenix 等）。沿"再补几个功能让它更完整"的思路走，等于在对手最强的地方正面追赶，吸引不到人。

**开源项目吸引人靠的不是功能多，而是在某一个点上比所有人都好。** 功能堆叠反而稀释这个点。九个半成品模块比一个做到极致的能力更劝退。

## 2. 楔子：面向测试团队的"多轮回归退化检测"

现有工具几乎全是 developer-first（CLI / SDK / YAML）。一个真实存在、却被系统性忽略的人群是：**传统 QA / 测试团队、业务侧验收人员 —— 不写代码、却要对 AI 输出质量负责的人。**

QTP 的楔子就落在这里，并进一步收窄到最有研究味、最没人做好的细分：

> **改了 Prompt / 模型 / 知识库后，多轮对话能力在哪一轮退化了、为什么。**

一句话定位：

> **QTP 把真实多轮对话沉淀为可回放的回归资产，在每次发布前发现 Prompt / 模型 / 知识库 / 工具链变更带来的质量退化，并定位到具体轮次与原因。**

## 3. 窄 ≠ 浅

容易混淆的关键点：

- **窄**指范围窄（只做多轮回归这一条链路）。
- **浅**指做得单薄（抽变量用正则、不处理随机性、诊断靠 LLM 瞎编）。

吸引人的是"窄而深"，劝退的是"广而浅"。几乎所有成功开源都是窄而深起家：promptfoo 起初只是跑 eval 的 CLU，Langfuse 起初只做 trace，ripgrep 就是"更快的 grep"。它们靠一件事做到第一被记住，而非功能多。

## 4. 竞品边界：Ragas 不是对手，是零件

| | Ragas / DeepEval | QTP |
|---|---|---|
| 形态 | Python 库 | Web 平台 |
| 用户 | 工程师 | 测试人员 / QA |
| 回答的问题 | 这次输出质量分多少 | 改版后哪些退化了、第几轮、为什么 |
| 核心动作 | 对输出打分 | 基线 vs 候选版本对比 + 发布门禁 |
| 多轮 | 以单轮为主 | 上下文追踪断言 |
| 失败处理 | 给一个分数 | 证据链 + 原因 + 修复建议 + 复核 |
| 资产来源 | 自备 / 合成数据集 | 录真实对话一键转用例 |

**比喻**：Ragas 是"食材 / 调料"，QTP 是"厨房 + 出餐流程"。Ragas 的指标完全可以作为 QTP 内部一种 Judge 接入（详细需求文档第 18.5 节已规划集成）。

**重要纪律**：绝不和 Ragas 拼"谁的分数算得准"——那是它们多年专注的领域，应该输也会输。QTP 的价值必须落在它们碰都不碰的四层。

## 5. 专业度落在哪：两种护城河

- **算法护城河**：谁的指标算得准 → 别人的战场，放弃。
- **系统护城河**：谁能把混乱的真实流程变成可复现、可信赖的闭环 → QTP 的战场，且更值钱。

把一个 metric 调用包装成"录真实对话 → 沉淀资产 → 跨版本回归 → 定位退化"的可靠系统，工程难度远高于写一个打分公式。QTP 路线上真正硬的技术问题：

1. **随机性下的回归判定（最硬，Ragas 不碰）**：LLM 输出非确定，"候选失败"是真退化还是采样噪声？需要多次采样、稳定性评分、置信区间，区分显著退化与正常波动。
2. **多轮上下文状态追踪（最差异化，有研究味）**：抽取变量、跨轮追踪更新、判断模型某轮引用了哪个版本的值。
3. **失败归因诊断**：把失败归到 Prompt / 模型 / 知识库 / 工具并给证据。
4. **异构接入抽象**：把 Dify / OpenAI / SSE / Webhook 统一成可回放的标准协议。

**结论**：专业能力强不强，不取决于选哪条路，取决于在选定的路上做到多深。把第 1、2 个问题做扎实，"专业能力不强"的担忧自动消失。

## 6. 一个战略张力：产品给测试人员，项目要卖给开发者

开源项目靠开发者传播（GitHub / 技术社区），但 QTP 的目标用户（不写代码的测试人员）不逛 GitHub。真实采纳链路是：**开发者 / QA 负责人在 GitHub 发现 → 部署起来给团队里的测试人员用。**

推论：
- README / Demo 必须**说服开发者**（一键起、能接 CI、Adapter 可扩展、Judge 可换模型），即便产品本身服务测试人员。
- CLI / CI / 自托管一键启动不是可选项，是被发现的前提。（路线图阶段 6，待系统主体成型后落地。）

## 7. 决策结论

1. 采纳"AI 应用回归测试平台"重定位与测试资产飞轮叙事。
2. 押注"多轮对话回归诊断"为唯一主线，单轮 / RAG / 安全 / 格式降级为后续。
3. 会话录制虽是原文档的核心入口，但定位为"资产来源"，排在多轮诊断之后（阶段 5）—— 真正的"哇"在诊断，不在录制。此排序已确认。
4. 资源集中投入阶段 2、3 两个硬骨头。
5. 对外采纳基建（README / docker 一键 / demo 数据 / 录屏 / CLI）放在系统主体成型之后（阶段 6）。
