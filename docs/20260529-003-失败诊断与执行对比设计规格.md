# 失败诊断与执行对比 — 设计规格（北极星屏）

> 文档定位：补齐设计师缺失的护城河三屏中的两屏 / 高保真稿输入 / 前端实现依据
> 配套：[ROADMAP.md](../ROADMAP.md) · [设计资产盘点](./20260529-002-设计资产盘点.md) · [数据模型](../packages/shared-database/prisma/schema.prisma)
> 前端约束：严格遵守 `apps/web/AGENTS.md`（Next.js 16 App Router · Radix UI · Tailwind v4 · oklch token · 禁止 mock-only 数据源）

本规格描述 QTP 唯一不可替代的两屏：**执行对比**（看见退化）与 **失败诊断**（解释退化）。它们对应北极星演示，是项目最该做深、也最缺设计的地方。

---

## 0. 北极星场景（这两屏共同要讲清的故事）

某多轮用例「员工数变更后的政策判定」：

1. 第 1 轮：用户说"我们公司 80 人"。
2. 第 2 轮：用户改口"调整为 20 人"。
3. 第 3 轮：用户问"我们符合小微企业认定吗"。

基线版本 prompt@1.4 第 3 轮正确使用 20 判定 → **通过**；
候选版本 prompt@1.5 第 3 轮仍用旧值 80 判定 → **失败**。

平台要让测试人员在不写代码的情况下看到：**这是一次真实退化（非抖动）、发生在第 3 轮、违反了"不得使用陈旧上下文"断言、大概率上下文未持久化、并给出修复方向。**

---

## 1. 屏 A：执行对比（Execution Comparison）

### 1.1 页面目标
比较同一回归套件在**基线 run** 与**候选 run** 上的结果，识别本次变更引入的退化。回答：候选是否退化？哪些用例从通过变失败？哪些被修复？是否建议发布？

### 1.2 路由与入口
- 路由：`/ai-quality-platform/apps/[appCode]/compare/[comparisonCode]`（新增，与既有 `history/[runCode]` 平级）
- 入口：执行历史列表「与基线对比」按钮、工作台版本对比卡片「查看详情」。

### 1.3 信息架构（自上而下）

| 区块 | 内容 | 数据来源 |
|---|---|---|
| ① 对比头 | 应用 · 套件 · 基线版本卡 `VS` 候选版本卡（版本号/Prompt/模型/Commit/执行时间/通过率/用例数） | `RegressionComparison` + 两个 `EvalRun` + `AppVersion` |
| ② 发布建议 | 综合风险等级 + 结论（可发布/需关注/需人工评估/不建议/阻断）+ 一句话理由 | 对比聚合 + 门禁规则 |
| ③ 对比指标卡 | 通过率变化 · 新增失败 · 修复失败 · 持续失败 · 稳定性得分 · 平均耗时变化 | 聚合 `EvalResult` 差异 |
| ④ 差异明细表 | 逐用例：基线结果 / 候选结果 / 结果变化 / 风险 / 失败类型 / 操作 | `EvalResult`(两个 run) 对齐 by caseId |
| ⑤ 退化类型分布 | 新增失败按诊断主类型分布（上下文/RAG/格式/超时/接口…） | `FailureDiagnosis.primaryType` |

### 1.4 关键交互
- 差异明细表过滤切片：`全部 / 新增失败 / 修复失败 / 持续失败 / 仅看差异`。默认落在「新增失败」——退化是用户来这页的目的。
- 行「查看诊断」→ 跳屏 B（失败诊断），带 `resultId`。
- 结果变化用色：新增失败=红、修复=绿、持续失败=橙、无变化=中性。
- **稳定性得分**（阶段 2 能力的前台出口）：每条差异旁标注"真退化 / 疑似抖动"标签 + 置信度 tooltip。这是与"打一次分"工具的可见分水岭，**必须出现在 UI 上**。

### 1.5 状态与空态
- 候选 run 未执行：卡片显示「请先执行候选版本」+ CTA「立即执行候选」。
- 基线候选相同：禁用对比并提示。
- 无差异：明细表空态「本次候选与基线无差异，未发现退化」。

## 2. 屏 B：失败诊断（Failure Diagnosis）

这是整个产品最重要的一屏。它把 PASS/FAIL 变成"为什么"。

### 2.1 路由与入口
- 路由：`/ai-quality-platform/apps/[appCode]/diagnosis/[resultId]`
- 入口：执行对比差异行、工作台待复核项、执行历史失败行。

### 2.2 信息架构（自上而下）

```
┌─ ① 用例摘要条 ────────────────────────────────────────┐
│ 用例名 · 失败状态(新增失败) · 套件 · 风险 · 基线✓/候选✗ · 诊断结论一句话 │
├─ ② 会话逐轮对比（页面核心，占最大面积）──────────────┤
│  左:基线回答(prompt@1.4)        右:候选回答(prompt@1.5)   │
│  逐轮并排；问题相同居中，回答分列；差异轮高亮            │
│  视图切换: [并排] [仅看差异] [完整日志]                  │
├─ ③ 断言与证据 ────────────────────────────────────────┤
│  失败断言: mustNotUseStaleContext.employee_count        │
│  期望:≠80  实际:80  结果:✗  置信度:高                    │
│  证据链(可点轮次定位): 第2轮改20 → 第3轮候选用80         │
├─ ④ 可能原因 (Top-N, 带置信等级) ─────────────────────┤
│  1) 上下文更新未持久化  [高]   2) 查询改写丢失条件 [中]   │
├─ ⑤ 修复建议 (可操作) ────────────────────────────────┤
│  · 系统提示加"始终使用对话中最新事实"                    │
│  · 第2轮后强制刷新 employee_count=20                     │
│  [复制] [生成修复版Prompt草稿]                           │
├─ ⑥ 执行/评估/性能成本 (折叠) ────────────────────────┤
├─ ⑦ 人工复核与处理 ───────────────────────────────────┤
│  复核结果: 确认失败/误报/模型正确/不确定                 │
│  处理: 创建缺陷/加白名单/重新评估/忽略  [提交复核]       │
└───────────────────────────────────────────────────────┘
```

### 2.3 逐轮对比（区块②）细节
- 每轮卡片字段：轮次、用户输入（居中或灰条）、AI 回答、状态、耗时、tokens。
- **差异高亮**：候选回答中"陈旧值 80"标红下划线；基线回答中"正确值 20"标绿。高亮区间来自断言命中的 `evidence.span`。
- 「仅看差异」只渲染存在断言失败或文本差异的轮次。
- 「完整日志」抽屉展示该轮 `requestJson` / `responseJson` 原始内容（敏感字段脱敏）。

### 2.4 证据链（区块③）
- 每条证据：来源（用户输入/AI回答/检索/工具日志）+ 轮次 + 高亮片段 + 可点击定位到区块②对应轮次。
- 证据按因果顺序排列，构成"为什么失败"的可读叙事。

### 2.5 可信度纪律（贯穿④⑤）
- 可能原因/修复建议来自 LLM，**置信度低于阈值不展示**（阈值见路线规划 Q4）。
- 宁可显示「暂无足够证据给出原因，建议人工复核」也不要瞎编——可靠度是这屏的生命线。
- 每条原因标注置信等级（高/中/低）与"参考证据数"，并可点开看证据。

### 2.6 复核闭环（区块⑦）
- 写入 `EvalReview`（已存在）：`manualResult` + `reviewComment`。
- 复核结论可覆盖自动判定的最终结论，但**保留原始自动评分**（审计可追溯）。
- 误报项进入「评估策略优化队列」（阶段 4 后续）。

## 3. 数据依赖（对照数据模型）

本规格依赖 [数据模型扩展](../packages/shared-database/prisma/schema.prisma) 中新增的：
- `AppVersion`：版本元数据（版本号/Prompt/模型/知识库/Commit）。
- `RegressionComparison`：一次基线 run × 候选 run 的对比及聚合结果。
- `EvalResult` 扩展：逐轮快照（`turnsJson`）、稳定性/采样字段（阶段 2）。
- `FailureDiagnosis`：诊断结论、主类型、证据链、可能原因、修复建议、置信度。
- `CaseAssertionResult`：逐断言结果（含上下文断言 expected/actual/span）。

> 既有 `EvalRun`/`EvalResult`/`EvalReview` 不破坏，只新增表与可空列，向后兼容。

## 4. 前端落地约束（摘要）
- 组件全部用 `src/components/ui/*`（Radix 封装）+ Tailwind utility；色彩用 oklch token，差异色新增 token 而非硬编码 hex。
- 逐轮对比左右分栏在 `< md` 降级为上下堆叠（AGENTS 响应式规范）。
- 视图/数据分离：页面在 `features/diagnosis/`、`features/comparison/`，请求在各自 `api/`，经 gateway。
- 禁止 mock：演示数据由 `pnpm db:seed` 写入一组北极星样本（阶段后续任务）。

## 5. 验收（这两屏做到即北极星成立）
1. 打开执行对比，默认能看到「新增失败」切片与发布建议。
2. 每条新增失败标注"真退化/疑似抖动"+置信度。
3. 点进失败诊断，逐轮对比能高亮第 3 轮的陈旧值 80 与基线正确值 20。
4. 证据链可点轮次定位；失败断言展示期望≠80/实际80。
5. 可能原因与修复建议在低置信度时不瞎编。
6. 能提交人工复核并覆盖结论、保留原始评分。
