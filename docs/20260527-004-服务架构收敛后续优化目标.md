# 服务架构收敛后续优化目标

作者：Codex

日期：2026-05-27

分支：`codex/service-consolidation-architecture`

## 当前结论

服务架构收敛第一阶段已经完成：

- 运行时后端服务收敛为 `quality-gateway`、`quality-platform-service`、`quality-execution-service`。
- 原 business、case、plan、ai、review、statistics、system 业务服务已经合并为 platform 内部模块。
- 公开 API 段保持兼容，前端仍通过 `/ai-quality-platform/api/{segment}/**` 访问。
- AI 评估调用的请求体、Qwen `enable_thinking: false`、usage 归一和失败结果结构已经抽入 `packages/ai-model-adapter`。
- 启动脚本、健康检查和健康页已经按 gateway/platform/execution 三个关键运行单元收敛。

这一阶段的目标是降低本地开发和部署复杂度，同时不牺牲真实业务链路。

## P0：合并前收口

目标：让本次大改可以安全进入主分支。

- 整理本分支提交，确认只包含服务收敛相关改动。
- 合并前再次运行 `pnpm check:health`、`pnpm -r --if-present typecheck`、`pnpm -r --if-present test`、`pnpm build:web`。
- 用浏览器复核健康页、模型中心、应用列表、应用概览、用例管理和执行计划。
- 合并到 `main` 后重新拉起服务，确认远端主分支也是三服务拓扑。

## P1：运行健康与依赖可观测

目标：健康页不只显示进程 UP，还能帮助定位真实故障。

- `quality-platform-service` 健康检查增加数据库连接状态。
- `quality-execution-service` 健康检查增加恢复扫描状态、当前运行任务数和最近 worker 错误。
- Redis 如果继续作为缓存或队列候选，需要在健康详情里显示连接状态，但不作为所有页面的硬依赖。
- 模型供应商连接测试从模型中心能力扩展为健康详情中的可选诊断项，避免供应商波动拖垮平台基础健康。
- 健康页增加“公开 API 段 -> 目标运行单元”的展示，便于排查 gateway 转发。

## P2：执行 Worker 可靠性

目标：把 execution service 从“能执行”强化到“可恢复、可观测、可控并发”。

- 为执行批次增加 worker heartbeat 和最后推进阶段时间。
- 明确 RUNNING 批次恢复策略：哪些状态可恢复，哪些状态需要人工介入。
- 让取消、全量重试、重新评估、重新计费都具备幂等保护。
- 把执行并发、评估并发和模型调用超时做成可配置项，并在执行详情中可追踪。
- 增加执行服务重启恢复的自动化测试或端到端脚本。

## P3：AI 模型调用标准继续下沉

目标：把 `ai-model-adapter` 从工具函数升级为稳定调用标准。

- 增加 ProviderAdapter 实现层，封装 OpenAI compatible 和 Qwen compatible 调用。
- 抽出费用计算辅助函数，统一 normal input、cached input、output token 的计费口径。
- 标准化模型错误码，例如超时、鉴权失败、限流、供应商 5xx、响应格式非法。
- 统一保存裁判模型请求、响应、usage、费用和耗时，保证审计字段不随供应商差异漂移。
- 当多个系统都需要统一 AI 出口、密钥隔离或限流治理时，再评估是否升级为独立 `quality-ai-invocation-service`。

## P4：Platform 内部模块边界治理

目标：合并服务后仍保持模块清晰，不退化成难维护的大单体。

- 为 `modules/app`、`modules/case`、`modules/plan`、`modules/provider`、`modules/review`、`modules/report`、`modules/auth` 增加模块级 README 或契约说明。
- 逐步抽出共享 DTO、分页结构和错误结构，减少模块之间复制类型。
- 建立模块间依赖规则：plan 可以读 case，report 可以汇总 app/case/plan/execution，但普通模块不要反向依赖 report。
- 对 platform service 增加高价值集成测试，覆盖应用创建、用例导入、计划创建、启动执行入口这些跨模块链路。

## P5：部署与 CI 收敛

目标：让三服务拓扑在本地、CI 和部署环境保持一致。

- Docker Compose 从旧多服务拓扑收敛为 web/gateway/platform/execution/mysql/redis。
- CI 增加三服务健康检查和关键页面 smoke test。
- 将 `WATCHPACK_POLLING=true` 这类本机 watcher 兜底写入本地启动文档，避免 EMFILE 问题反复排查。
- 梳理环境变量，删除旧服务端口变量，保留公开 API 段与部署服务映射。
- 合并后建立一次迁移验收清单，确认主分支、远端分支、本地运行环境一致。

## 推荐推进顺序

1. 先做 P0，确保当前分支可以安全提交、合并、远端主分支可用。
2. 再做 P1 和 P2，因为它们直接提升排障和执行稳定性。
3. P3 可以跟执行评估成本审计继续结合推进。
4. P4 和 P5 作为工程治理任务，适合在下一次大功能前完成。
