# 执行评估两阶段与计费审计计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将执行计划升级为“接口执行、评估执行、token 与费用汇总”三段式持久化任务，并完整记录评估模型调用输入输出、token 用量和多档模型费用。

**Architecture:** `quality-execution-service` 作为执行编排入口，`start.do` 只做启动校验、创建不可猜测执行批次和用例快照；持久化 worker 按阶段推进接口调用和评估调用，所有阶段状态写入 DB，服务重启后可继续未完成任务。应用接口调用并发数来自接口配置，评估调用并发数来自评估配置；评估模型 usage 经过归一化后写入审计表，再按模型中心配置的普通输入、缓存命中输入、输出价格计算费用。

**Tech Stack:** Prisma/MySQL, NestJS services, Next.js App Router, React 19, Tailwind, Vitest, Testing Library.

---

## 1. Current State

- `apps/quality-execution-service/src/execution.service.ts` 当前在单个 case 流程内完成“应用接口调用 -> 评估模型调用 -> 创建 eval_result”，整体按用例顺序串行执行。
- `EvalRun` 只有总体状态、通过/失败/待确认数量、均分和起止时间，无法表达接口阶段、评估阶段和费用计算阶段。
- `EvalResult` 已保存应用请求、响应、实际回答和评分结果，但没有区分接口状态与评估状态，也没有保存评估模型的完整 request、response、usage 和费用明细。
- `AiApp.adapterConfig` 已承载接口模板、响应路径和流式配置，适合继续存放接口执行并发数。
- `AppEvaluationConfig` 已是应用级评估配置，适合新增评估并发数。
- `AiModel.limitsJson` 已承载模型限制类配置，适合扩展计价配置，不需要为首期价格配置新增模型表字段。

## 2. Target Runtime Flow

### 2.1 Start Preflight

`POST /execution/start.do` 保持对外入口不变，但启动逻辑调整为：

- 读取并校验 `EvalPlan`、`AiApp`、`AppEvaluationConfig`、`AiModel`、`AiProvider`。
- 若评估配置不存在、模型不可用、供应商不可用、供应商缺少 `baseUrl` 或 `apiKey`，直接返回明确错误，不创建 `EvalRun`。
- 解析计划范围并生成本次用例快照，快照包含问题分类、问题内容、期望回答和原始 input/expected JSON。
- 创建不可猜测 `runCode`，写入 `EvalRun(status=RUNNING, phase=APP_CALLING)`。
- 为每个用例创建一条 `EvalResult` 占位记录，避免执行中刷新页面时看不到本次任务范围。
- 将 `EvalRun` 作为持久化队列记录交给 worker 继续推进。

### 2.2 Phase: APP_CALLING

- worker 从 `EvalRun.phase=APP_CALLING` 的运行批次恢复任务。
- 按 `AiApp.adapterConfig.execution.appConcurrency` 控制应用接口调用并发，默认 `3`，最小 `1`，最大 `10`。
- 每条用例渲染协议模板并调用被测应用接口。
- 成功时写入 `EvalResult.requestJson`、`responseJson`、`finalAnswer`、`appElapsedMs`、`appStatus=PASSED`。
- 接口失败、HTTP 非成功、成功表达式不通过或无法提取回答时，写入 `appStatus=FAILED`、`evaluationStatus=SKIPPED`、`passStatus=FAIL`、`errorCode` 和 `failureReason`。
- 所有接口调用结束后，将 `EvalRun.phase` 更新为 `EVALUATING`。

### 2.3 Phase: EVALUATING

- worker 只挑选 `appStatus=PASSED` 且 `evaluationStatus` 未完成的结果进入评估。
- 按 `AppEvaluationConfig.evaluationConcurrency` 控制评估模型调用并发，默认 `3`，最小 `1`，最大 `10`。
- 每次评估调用前构造 OpenAI-compatible chat request，使用应用评估配置中的系统默认提示词或自定义提示词。
- 每次评估调用都创建或更新一条 `EvalJudgeCall` 审计记录，保存完整 request、response、raw usage、归一化 token、费用明细、状态、错误和耗时。
- 评估成功后，将模型返回的 `passStatus`、`score`、`reason`、`problemType` 写回 `EvalResult`。
- 评估失败时，当前结果标记 `evaluationStatus=FAILED`、`passStatus=FAIL`、`errorCode=JUDGE_EVALUATION_FAILED`，并保留 judge request 和错误响应或错误消息。
- 所有可评估结果结束后，将 `EvalRun.phase` 更新为 `COSTING`。

### 2.4 Phase: COSTING

- 读取本次 `EvalJudgeCall` 的 usage 和模型当前价格配置。
- 对每条 judge call 归一化 token 类型并计算分项费用。
- 汇总到 `EvalRun`：普通输入 token、缓存命中输入 token、输出 token、总 token、分项费用、总费用、币种和计费状态。
- 缺 usage 时不估算，标记 `NO_USAGE`。
- 缺价格时保留 token，金额为空，标记 `SKIPPED_NO_PRICE`。
- 全部计算结束后，将 `EvalRun.status=COMPLETED`、`phase=COMPLETED`。

## 4. Usage Normalization and Cost Rules

新增 usage 归一化逻辑，建议放在 `apps/quality-execution-service/src/judge-usage.ts`，由执行服务调用。

### 4.1 Normalized Shape

```ts
export interface NormalizedJudgeUsage {
  rawUsage: Record<string, unknown>;
  normalInputTokens: number | null;
  cachedInputTokens: number | null;
  outputTokens: number | null;
  totalTokens: number | null;
  usageStatus: 'AVAILABLE' | 'NO_USAGE' | 'UNSUPPORTED';
}
```

### 4.2 Provider Rules

- OpenAI-compatible 常规字段：
  - `prompt_tokens` 或 `input_tokens` -> 输入 token
  - `completion_tokens` 或 `output_tokens` -> 输出 token
  - `total_tokens` -> 总 token
- DashScope/Qwen cache 字段：
  - `usage.prompt_tokens_details.cached_tokens` 表示缓存命中输入 token。
  - DashScope 原生模式里 cached token 是 `input_tokens` 的一部分，普通输入 token = `input_tokens - cached_tokens`。
  - Anthropic-compatible 字段如 `cache_read_input_tokens` 单独报告时，普通输入 token 不扣减该字段。
- 无法识别 usage 时：
  - 保存 raw response。
  - 标准 token 字段写 `null`。
  - cost status 写 `NO_USAGE`，不做估算。

参考资料：

- 阿里云百炼 Context Cache：`usage.prompt_tokens_details.cached_tokens`
- 阿里云百炼流式输出示例：`usage.input_tokens`、`usage.output_tokens`、`usage.prompt_tokens_details.cached_tokens`

### 4.3 Cost Rules

新增成本计算逻辑，建议放在 `apps/quality-execution-service/src/judge-cost.ts`。

```ts
export interface ModelPricing {
  currency: 'CNY';
  unit: 'PER_MILLION_TOKENS';
  normalInputPrice?: number | null;
  cachedInputPrice?: number | null;
  outputPrice?: number | null;
  cacheWriteInputPrice?: number | null;
}
```

计算规则：

- 普通输入费用 = `normalInputTokens / 1_000_000 * normalInputPrice`
- 缓存命中输入费用 = `cachedInputTokens / 1_000_000 * cachedInputPrice`
- 输出费用 = `outputTokens / 1_000_000 * outputPrice`
- 总费用 = 三项费用之和。
- 某类 token 有数量但对应价格为空时，该类费用为空，本次调用 `costStatus=SKIPPED_NO_PRICE`。
- 所有需要计费的 token 都有价格时，`costStatus=CALCULATED`。

## 9. Compatibility and Migration

- 历史 `EvalRun` 没有 `phase` 时，读取层按 `COMPLETED` 处理，避免旧执行记录显示为运行中。
- 历史 `EvalResult` 没有 `appStatus` 和 `evaluationStatus` 时，读取层根据 `passStatus` 推导为已完成。
- 历史记录没有 `EvalJudgeCall` 时，详情页展示“该执行记录未保存评估调用审计”。
- 历史模型没有 `limitsJson.pricing` 时，费用展示为“未配置价格”，不阻塞执行。
- `runCode` 和 `planCode` 已经改为不可猜测编码，本计划继续沿用，不重新迁移历史 ID。

## 10. Acceptance Criteria

- 执行计划触发后，执行记录立即可见，页面显示接口阶段进度。
- 接口阶段未全部结束前，不开始评估阶段。
- 接口阶段结束后，页面切换到评估阶段进度。
- 每条评估调用都有完整 request、response、usage 和错误信息审计。
- Qwen cached token 能从 usage 中识别并按缓存命中输入价格单独计费。
- usage 缺失时不估算 token，不产生费用。
- 价格缺失时 token 正常展示，费用为空，并可在补充价格后重新计算。
- 服务重启后，未完成 run 能从 DB 恢复并继续执行，不重复已完成接口调用或评估调用。
- 前端配置页、计划页、历史详情页均通过自动化测试和浏览器真实验收。
