# 服务架构收敛设计

作者：Codex

日期：2026-05-27

分支：`codex/service-consolidation-architecture`

## 1. 背景

当前 AI 质量平台后端按较细的业务域拆成 8 个 NestJS 服务：

- `quality-business-service`
- `quality-case-service`
- `quality-plan-service`
- `quality-execution-service`
- `quality-ai-service`
- `quality-review-service`
- `quality-statistics-service`
- `quality-system-service`

再加上 `quality-gateway` 和 `web`，本地开发需要同时维护较多进程、端口、健康检查和转发规则。这个拆法在早期有利于把功能域快速铺开，但现在已经出现几个问题：

1. 多数服务只是 CRUD 或查询模块，没有独立扩缩容、故障隔离或独立部署的必要。
2. 多个服务共享同一套数据库和业务实体，服务边界更多体现为文件夹边界，而不是清晰的运行时边界。
3. 健康检查、启动脚本、网关转发和本地排障复杂度被放大。
4. 执行链路已经演进为持久化 worker 模式，和普通业务 CRUD 的运行特征明显不同，应该单独保留边界。
5. 当前 `quality-ai-service` 主要承担供应商与模型配置管理，还不是完整的 AI 模型调用网关。仅因为“模型配置”而独立部署，收益不明显。

本设计的目标是把“业务模块边界”和“独立服务边界”重新区分开，减少不必要的进程数量，同时保留未来扩展 AI 调用标准、异步执行和统一网关治理的空间。

## 2. 设计结论

推荐收敛为以下运行时拓扑：

```text
Next.js Web
  |
  | /ai-quality-platform/api/**
  v
quality-gateway
  |
  +--> quality-platform-service
  |      - 应用管理
  |      - 用例管理
  |      - 计划管理
  |      - 模型供应商与模型配置
  |      - 人工复核
  |      - 统计报表
  |      - 系统登录与基础配置
  |
  +--> quality-execution-service
  |      - 执行批次创建
  |      - APP_CALLING / EVALUATING / COSTING 阶段推进
  |      - 任务恢复
  |      - 结果明细
  |      - 评估调用审计
  |      - 费用重算
  |
  +--> quality-ai-invocation-service
         - 内部 AI 模型调用运行时
         - 不映射宿主机端口
         - 统一外部模型供应商调用入口
         +--> ai-invocation-contract package
              - 纯请求响应契约、usage 归一和失败结果结构
         +--> ai-model-adapter package
              - 协议 SDK
              - 统一模型调用、费用计算和供应商差异处理
```

目标不是回到单体应用，而是把服务数量压缩到真正需要独立运行的边界：

| 运行单元 | 是否独立进程 | 保留原因 |
| --- | --- | --- |
| `web` | 是 | 前端 Next.js 应用，独立开发和构建 |
| `quality-gateway` | 是 | 统一入口、文根、跨域、鉴权、日志、限流和未来治理 |
| `quality-platform-service` | 是 | 常规业务管理模块集中承载，减少无意义微服务拆分 |
| `quality-execution-service` | 是 | 长耗时异步任务、恢复、重试和阶段推进需要独立运行边界 |
| `quality-ai-invocation-service` | 是 | 统一外部模型调用运行时，避免 platform/execution 各自直连供应商 |
| `ai-invocation-contract` | 否，package | 纯请求响应契约，被 client、AI invocation service 和 adapter 共享 |
| `ai-model-adapter` | 否，package | 协议 SDK，被 AI invocation service 复用 |

## 3. 服务拆分原则

一个模块只有满足以下条件之一，才适合成为独立服务：

1. **运行特征不同**：例如常驻 worker、长耗时任务、队列消费、批量执行。
2. **扩缩容需求不同**：例如执行任务高峰期需要单独扩 worker，而管理页面接口不需要扩容。
3. **故障隔离价值明确**：例如模型供应商调用不稳定时，不应该拖垮核心管理接口。
4. **安全或网络边界不同**：例如统一模型调用网关未来可能需要单独密钥隔离、审计和限流。
5. **有多个消费者复用**：例如 AI 调用标准被执行服务、协议测试、未来其他业务系统复用。

反过来，如果只是同库 CRUD、同一个用户入口、同一套发布节奏、同一套权限模型，则优先作为 `quality-platform-service` 内部模块，而不是独立进程。

## 4. 当前服务归并设计

| 当前服务 | 当前职责 | 目标归属 | 说明 |
| --- | --- | --- | --- |
| `quality-gateway` | 统一 HTTP 入口和反向代理 | 保留 | 从“按服务名转发”升级为“按公开 API 段转发到目标运行单元” |
| `quality-business-service` | 应用管理、协议配置、评估配置 | 并入 `quality-platform-service` | 这是主业务服务核心模块 |
| `quality-case-service` | 系统预置用例、应用用例、分类、CSV/Excel | 并入 `quality-platform-service` | 属于质量资产管理，不需要独立进程 |
| `quality-plan-service` | 执行计划 CRUD、预览、启动包装 | 并入 `quality-platform-service` | 计划定义归平台服务；真正执行由 execution service 承接 |
| `quality-ai-service` | 供应商、模型配置、模型连接测试 | 配置并入 `quality-platform-service`，模型调用运行时进入 `quality-ai-invocation-service` | 不保留旧配置型 AI 服务；真正独立的是内部 AI invocation 边界 |
| `quality-review-service` | 人工复核提交与查询 | 并入 `quality-platform-service` | 人工修订是结果管理模块的一部分 |
| `quality-statistics-service` | 工作台统计、报告生成与导出 | 并入 `quality-platform-service` | 当前统计主要是同库查询，独立服务收益低 |
| `quality-system-service` | 登录、健康检查 | 并入 `quality-platform-service` | 系统基础能力不需要单独进程 |
| `quality-execution-service` | 执行、评估、计费、恢复、重试 | 保留，并演进为 worker/execution service | 运行特征与其他模块不同，应该独立 |

## 5. API 兼容策略

外部 API 路径先保持不变，避免前端大面积修改。

当前前端访问形态：

```text
/ai-quality-platform/api/business/**
/ai-quality-platform/api/case/**
/ai-quality-platform/api/plan/**
/ai-quality-platform/api/execution/**
/ai-quality-platform/api/ai/**
/ai-quality-platform/api/review/**
/ai-quality-platform/api/statistics/**
/ai-quality-platform/api/system/**
```

收敛后仍保留这些公开段。变化只发生在 gateway 内部：

| 公开 API 段 | 目标服务 |
| --- | --- |
| `business` | `quality-platform-service` |
| `case` | `quality-platform-service` |
| `plan` | `quality-platform-service` |
| `ai` | `quality-platform-service` |
| `review` | `quality-platform-service` |
| `statistics` | `quality-platform-service` |
| `system` | `quality-platform-service` |
| `execution` | `quality-execution-service` |

示例：

```text
/ai-quality-platform/api/business/app/list.do
  -> quality-platform-service /ai-quality-platform/app/list.do

/ai-quality-platform/api/case/case/list.do
  -> quality-platform-service /ai-quality-platform/case/list.do

/ai-quality-platform/api/ai/provider/model/list.do
  -> quality-platform-service /ai-quality-platform/provider/model/list.do

/ai-quality-platform/api/execution/execution/start.do
  -> quality-execution-service /ai-quality-platform/execution/start.do
```

这样做有三个收益：

1. 前端 API 调用层可以基本不动。
2. 用户收藏地址、页面行为和 `.do` 风格接口保持稳定。
3. 后端可以分阶段迁移，不需要一次性移动所有模块。

## 6. `quality-platform-service` 模块边界

`quality-platform-service` 是主业务服务，不是把所有代码揉成一个大文件。它内部应按模块组织：

```text
apps/quality-platform-service/src/
  main.ts
  health.controller.ts
  modules/
    app/
      app.controller.ts
      app.service.ts
    case/
      case.controller.ts
      case.service.ts
      case-excel.service.ts
    plan/
      plan.controller.ts
      plan.service.ts
    provider/
      provider.controller.ts
      provider.service.ts
    review/
      review.controller.ts
      review.service.ts
    report/
      report.controller.ts
      report.service.ts
    auth/
      auth.controller.ts
      auth.service.ts
```

模块之间通过明确接口协作，避免在服务内部形成新的隐式耦合：

- `plan` 模块负责计划定义、筛选预览和状态管理。
- `case` 模块负责用例资产、分类、预置引用、CSV/Excel。
- `provider` 模块负责模型供应商与模型配置，不直接承载复杂执行评估。
- `review` 模块负责人工修订记录。
- `report` 模块负责同库统计和报告数据。
- `auth` 模块负责登录和当前用户上下文。

如果某个模块后续出现独立运行诉求，再从 `quality-platform-service` 中拆出会更有依据。

## 7. `quality-execution-service` 边界

执行服务继续独立，原因是它已经具备 worker 服务特征：

- `start.do` 只做校验、创建 run/result 占位和触发执行。
- 后台按 `APP_CALLING -> EVALUATING -> COSTING` 推进。
- 服务启动时需要扫描 `RUNNING` 批次并恢复未完成任务。
- 需要记录 `EvalJudgeCall` 审计、token usage、费用、耗时和错误信息。
- 需要处理取消、重试、重新评估、费用重算等长链路动作。

目标职责：

```text
quality-execution-service
  - 执行批次生命周期
  - 单条结果生命周期
  - 应用接口调用
  - 裁判模型评估调用
  - usage 归一和费用汇总
  - RUNNING 批次恢复
  - 执行详情查询
  - 评估调用审计查询
```

阶段一建议保持执行服务直接访问数据库。原因是当前执行恢复依赖 `eval_run`、`eval_result` 等持久化状态，如果改成大量跨服务 HTTP 调用，反而会增加失败点和恢复复杂度。

后续如果执行量上升，可以再把 HTTP 查询接口和 worker 消费进程拆开：

```text
quality-execution-api-service
quality-execution-worker-service
```

这不是本次收敛的第一阶段目标。

## 8. AI 模型调用标准

当前 `quality-ai-service` 不建议原样保留为独立服务，因为它主要做 provider/model 配置 CRUD。真正应该标准化的是“模型调用能力”。

第一阶段新增内部 AI invocation service，并保留纯契约 package 与供应商协议 package：

```text
apps/quality-ai-invocation-service/
packages/ai-invocation-contract/
packages/ai-model-adapter/
```

核心接口：

```ts
export interface ModelInvocationRequest {
  traceId: string;
  providerCode: string;
  modelId: string;
  protocol: 'OPENAI_COMPATIBLE' | 'QWEN_COMPATIBLE';
  messages: Array<{ role: 'system' | 'user' | 'assistant'; content: string }>;
  temperature?: number;
  responseFormat?: 'json_object' | 'text';
  stream?: boolean;
  enableThinking?: boolean;
  timeoutMs?: number;
}

export interface NormalizedModelUsage {
  normalInputTokens?: number;
  cachedInputTokens?: number;
  outputTokens?: number;
  totalTokens?: number;
  rawUsageJson?: Record<string, unknown>;
}

export interface ModelInvocationResult {
  status: 'SUCCEEDED' | 'FAILED';
  content?: string;
  responseJson?: Record<string, unknown>;
  rawResponseText?: string;
  usage?: NormalizedModelUsage;
  elapsedMs: number;
  errorCode?: string;
  errorMessage?: string;
}

export interface ProviderAdapter {
  testConnection(): Promise<ModelInvocationResult>;
  invoke(request: ModelInvocationRequest): Promise<ModelInvocationResult>;
}
```

AI invocation service 负责：

- 接收 platform/execution 的内部模型调用请求。
- 统一访问外部模型供应商，不映射生产宿主机端口。
- 后续承接密钥隔离、限流、调用审计和失败重试。

`ai-invocation-contract` package 负责：

- 纯请求/响应类型。
- usage 字段归一，例如 cached token。
- 稳定失败结果结构。

`ai-model-adapter` package 负责：

- OpenAI compatible 请求体生成。
- Qwen compatible 请求体差异，例如评估调用默认 `enable_thinking: false`。
- 超时、错误码、原始响应保留。
- 费用计算辅助函数。

平台服务负责管理供应商和模型配置，执行服务负责评估编排；两者都通过 AI invocation service 发起模型调用，不直接访问外部供应商，也不依赖供应商协议 SDK。

## 9. 配置与健康检查调整

当前 `shared-config` 同时表达“公开 API 段”和“后端独立服务”。收敛后应拆成两个概念：

```ts
type PublicApiSegment =
  | 'business'
  | 'case'
  | 'plan'
  | 'execution'
  | 'ai'
  | 'review'
  | 'statistics'
  | 'system';

type DeployableServiceKey =
  | 'web'
  | 'gateway'
  | 'platform'
  | 'execution'
  | 'aiInvocation';
```

推荐目标端口：

| 运行单元 | 端口 |
| --- | --- |
| `web` | `3000` |
| `quality-gateway` | `8080` |
| `quality-platform-service` | `3101` |
| `quality-execution-service` | `3104` |
| `quality-ai-invocation-service` | `3105` |
| MySQL | `3306` |

健康检查也需要从“8 个业务服务是否 UP”调整为“关键运行单元和依赖是否 UP”：

| 检查项 | 说明 |
| --- | --- |
| gateway | 统一入口是否可用 |
| platform | 主业务服务是否可用，数据库连接是否正常 |
| execution | 执行服务是否可用，恢复扫描是否正常 |
| database | MySQL 连接状态 |
| model providers | 不作为基础健康硬依赖，可放在模型中心或服务健康详情里展示 |

## 10. 迁移阶段

### 阶段 0：文档确认

产出：

- 本设计文档。
- 用户确认目标拓扑、API 兼容策略和迁移顺序。

不做：

- 不修改运行代码。
- 不删除旧服务。

### 阶段 1：引入 platform 服务骨架

产出：

- 新增 `apps/quality-platform-service`。
- 先迁移 `business`、`system` 两个低风险模块。
- 保持旧服务仍可启动。
- gateway 支持把 `business`、`system` 公开段转发到 platform。

验收：

- 应用列表、应用详情、登录或系统健康仍正常。
- `/api/business/**` 外部路径不变。
- `pnpm --filter quality-platform-service test` 通过。

### 阶段 2：迁移 case、plan、review、statistics、ai 配置模块

产出：

- 用例管理、计划管理、人工复核、统计报表、模型配置迁入 platform。
- gateway 将对应公开段转发到 platform。
- 旧服务进入废弃状态，但暂不删除。

验收：

- 预置用例和应用用例导入导出正常。
- 执行计划列表、预览和启动入口正常。
- 人工修订状态可以正常提交和恢复。
- 工作台、应用概览和报告统计正常。
- 模型中心供应商、模型 CRUD 和连接测试正常。

### 阶段 3：保留并强化 execution 服务

产出：

- `quality-execution-service` 保持独立。
- 明确其 worker 职责和 HTTP 查询职责。
- 将模型调用运行时抽到 `quality-ai-invocation-service`，协议差异保留在 `packages/ai-model-adapter`。

验收：

- 新建执行批次后能推进到完成。
- 服务重启后能恢复 `RUNNING` 批次。
- 评估调用审计、usage、费用和详情页展示不退化。
- 取消、全量重试、重新评估和重新计费可用。

### 阶段 4：收敛脚本、配置和健康页

产出：

- 根脚本从 `dev:services` 批量启动 8 个旧业务服务，调整为启动 platform、execution 和 AI invocation。
- `shared-config` 区分公开 API 段和真实部署服务。
- 健康页展示新的关键运行单元。
- 删除或归档旧服务目录。

验收：

- `pnpm check:health` 输出 gateway、platform、execution、AI invocation 等目标状态。
- 前端通过 `127.0.0.1` 和局域网 IP 访问都能加载业务数据。
- 旧 API 路径仍兼容。
- 仓库里不再保留无入口、无脚本、无引用的废弃服务。

## 11. 风险与约束

1. **一次性搬迁风险高**

   不建议一次删除 6 个服务。应该先让 platform 和旧服务并存，再逐段改 gateway 路由。

2. **不要把 service class 互相硬 import 成一团**

   合并成 platform 后仍要保持模块目录、DTO、测试和服务职责清晰。否则只是从“微服务过度拆分”变成“大文件单体”。

3. **执行服务不要过早改为纯 HTTP 编排**

   执行恢复依赖数据库状态，第一阶段 worker 直接读写 DB 更稳定。等队列和边界成熟后，再考虑 platform API 化。

4. **AI 调用运行时独立，但不对外暴露**

   `quality-ai-invocation-service` 是 Docker 内网服务，只做外部模型调用边界和后续治理承载；模型配置 CRUD 仍归 platform，避免恢复旧 `quality-ai-service` 的过度拆分。

5. **外部 API 稳定性优先**

   前端已经形成大量 `getGatewayApiUrl('case', ...)`、`getGatewayApiUrl('execution', ...)` 调用。第一阶段保持公开 API 段不变，避免把架构收敛变成前后端全链路重写。

## 12. 验收清单

完成服务收敛后，至少验证以下链路：

- 根路径 `/` 自动跳转到 `/ai-quality-platform`。
- 局域网 IP 访问前端时，业务接口仍通过同 host gateway 正常加载。
- 服务健康页显示新的关键运行单元，而不是旧的 8 个业务服务。
- 模型中心供应商和模型列表、创建、编辑、启停、连接测试正常。
- AI 应用列表、创建、详情、协议配置、评估配置正常。
- 系统预置用例和应用用例列表、分类、CSV 导入导出正常。
- 执行计划列表、预览、启动正常。
- 执行详情显示分阶段进度、结果、人工修订、评估调用审计和费用信息正常。
- 执行服务重启后能恢复未完成批次。
- `pnpm test`、`pnpm typecheck`、目标健康检查通过。

## 13. 推荐下一步

建议先按以下顺序推进：

1. 评审本设计文档，确认目标拓扑为 `gateway + platform + execution + AI invocation + ai-invocation-contract + ai-model-adapter`。
2. 编写实施计划，拆成可独立验收的迁移任务。
3. 先做 platform 骨架和 gateway 路由映射，不移动执行服务。
4. 逐模块迁移业务服务，并保持公开 API 路径不变。
5. 最后收敛启动脚本、健康页和旧服务目录。

这个顺序可以最大程度降低风险，也符合当前系统已经形成的真实页面验收习惯。
