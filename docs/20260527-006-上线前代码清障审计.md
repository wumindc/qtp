# 上线前代码清障审计

## 目标

面向首次上线，持续清理无用、冗余、兼容、重复、废弃、临时、虚拟和不真实的代码、配置、文档与数据结构。每一批清理必须有当前仓库证据和验证命令支撑，不能只凭文件名猜测。

## 第一批已处理

- 删除 `.codex/skills/semi-ui-skills`、`.superpowers/brainstorm`、`docs/superpowers/*` 和 `docs/semi-frontend-standards.md`。
  - 原因：这些是 Semi/HeroUI/脑暴/POC 过程产物，已与当前 `apps/web/AGENTS.md` 规定的 Radix + shadcn + Tailwind 主线冲突。
- 删除 `apps/web/src/components/console/*`。
  - 原因：未被任何页面引用，且使用旧 CSS class 形态，不符合当前 Tailwind-only 页面规范。
- 删除 `apps/web/src/app/providers.tsx`、`apps/web/src/lib/api/query-client.ts`、`apps/web/src/features/models/model-center-queries.ts`。
  - 原因：TanStack Query POC 层已无页面接入，当前模型中心使用显式 API 调用和本地状态。
- 删除 `apps/web/src/app/api/proxy/route.ts`。
  - 原因：前端 Next 侧任意 URL 代理属于上线风险口子。接口测试已改为通过后端 `/app/protocol/test.do` 执行，仍支持测试未保存的当前协议表单。
- 删除前端协议模板工具 `apps/web/src/features/apps/protocol-template.ts`。
  - 原因：协议模板渲染已统一下沉到后端服务，避免前后端各自解释模板。
- `apps/quality-ai-invocation-service`、`packages/ai-invocation-contract`、`packages/ai-invocation-client` 和 `packages/ai-model-adapter` 承接统一 AI 调用边界。
  - 原因：AI 调用抽象不应只停留在 execution 工具函数；模型中心的供应商模型发现、Chat/Embedding 测试和 execution 评估都通过内部 AI invocation service 发起，platform/execution 只依赖 `ai-invocation-client` 与纯契约 `ai-invocation-contract`，外部模型供应商调用和协议细节集中在 AI invocation 边界内处理。
- 收口 AI reasoning/thinking 参数抽象。
  - 原因：platform 的模型测试和 execution 的评估调用曾仍然知道 DeepSeek 的 `thinking.type` wire payload。当前业务服务只传抽象 `providerKind` 和 `enableThinking` 能力开关；Qwen `enable_thinking` 与 DeepSeek `thinking.type` 由 `packages/ai-model-adapter` 在 `quality-ai-invocation-service` 边界内统一翻译，评估调用对 Qwen/DeepSeek 均默认关闭 thinking。
- 删除 AI 调用契约的万能供应商透传口。
  - 原因：`providerOptions?: Record<string, unknown>` 会把任意供应商字段原样带入 Chat/Embedding 请求体，属于首次上线不应保留的“以后兼容”逃生口；`reasoningEffort?: unknown` 也会让非法对象被发送成供应商 `reasoning_effort`。当前调用契约只保留显式字段，`reasoningEffort` 收窄为枚举，adapter 会忽略运行时非法 reasoning 值，`scripts/check-topology.mjs` 也会阻止这些 raw provider escape hatch 回流。
- 删除用例套件 `eval_case_suite`、`/case/suite/**`、旧 `/case/import.do` 和旧 `/case/preset/import-to-app.do`。
  - 原因：当前真实流程是系统预置分类订阅和 CSV 导入，执行计划不再读取用例套件；继续保留会形成上线前废弃表、废弃端点和重复导入路径。
- 收窄用例 API 的旧兼容字段。
  - 原因：前端和后端创建/更新用例统一使用 `categoryId/query/expectedBehavior/enabled`，不再接受 `categoryCode/caseCode/code/riskLevels` 等第一次开发过程中的兼容别名或隐藏筛选条件。
- 删除用例分类 `code` 旧别名和 seed 风格空字段构造。
  - 原因：用例分类对外字段已经有正式 `id`，继续返回 `code = id` 会保留重复旧契约；`toCaseRecordFromSeed()` 还会把缺失的应用编码、分类、问题内容和期望回答补成空字符串。当前分类公开契约只返回 `id/name/description/enabled/sortOrder/appCode`，创建用例必须提交真实 `appCode/categoryId/query/expectedBehavior`。
- 删除未接入真实链路的 `ScoringService` 规则评分 POC。
  - 原因：当前评估由 execution service 调用模型裁判并审计 usage/费用，规则评分服务只被自身测试引用，保留会造成双评分路径的误解。
- 删除 `eval_report` 表和 `/report/list|detail|generate|export` 假报告链路，仅保留真实工作台统计 `/report/dashboard.do`。
  - 原因：前端没有报告生成/导出入口，原实现只写入空分类、空风险、空失败示例和空建议，属于不真实功能。
- 删除 `eval_case` 中未参与当前业务链路的 `caseName/riskLevel/sourcePresetId/referenceAnswer/minScore/manualReviewRequired/tags/version`，以及 `eval_run.warningCount/blockedCount`、`eval_result.ruleScore/judgeScore`。
  - 原因：这些字段不被当前用例管理、计划筛选、执行评估、复核或页面展示使用；保留会暗示不存在的风险分级、双评分和阻断统计能力。
- 删除旧版执行批次编码时间解析。
  - 原因：当前批次编码已经统一为不可预测 `run-xxxxxxxxxx`，执行排序和时间展示应只依赖数据库 `startAt/endAt`，不再从旧 `_RUN_` 编码里兼容解析时间戳。
- 收窄未使用的前端类型和 UI 基础组件导出。
  - 覆盖：旧评估/执行类型、前端过滤历史函数、`DropdownMenuRoot` 兼容别名和未使用的 shadcn wrapper 导出。
- 清理未使用依赖。
  - 覆盖：`@tanstack/react-query`、`jsonpath-plus`、`geist`、platform-service 重复 Prisma 依赖、根级重复 `vitest`、shared-database 直接 `mariadb` 依赖。
- 删除 `docs/20260526-001~005` 旧实施稿和本地 `.DS_Store`。
  - 原因：这些文档仍引用旧独立服务、旧 `caseName`/双评分字段、mock 初期页面和已废弃 worker 计划，会误导首次上线后的真实架构认知；当前有效设计以 `docs/ai-quality-platform-design.md`、`docs/20260527-002~006` 为准。
- 删除 Redis 运行依赖、健康探测和文档承诺。
  - 原因：当前执行 Worker 直接通过 MySQL 持久化状态推进，业务代码没有 Redis 队列、缓存或锁；继续在 compose、环境变量和健康页中保留 Redis 会制造不真实依赖。
- 替换本地假登录和明文默认管理员密码。
  - 原因：`admin/admin123456`、明文 seed 密码和 `local-admin-token-*` 只适合初期演示，不适合首次上线。当前改为 `QTP_ADMIN_INITIAL_PASSWORD` 显式初始化哈希密码、`shared-auth` 生成签名 token，gateway 对业务 API 校验登录态。
- 替换生产 Docker 中的 root/root 数据库连接。
  - 原因：生产 compose 不应硬编码 root 密码，也不应让 platform/execution 使用 root 账号连接业务库；当前 MySQL root 密码、应用库账号、应用库密码和库名都由环境变量显式提供，开发依赖 compose 使用独立的 `qtp_app` 本地账号。
- 补齐被测应用调用地址的生产环境边界。
  - 原因：前端任意代理删除后，后端协议测试和执行服务仍会按配置调用 `invokeUrl`。生产环境现在默认阻止 `localhost`、回环地址、内网 IP 和 Docker 内部服务名，确需访问受控内网业务系统时必须通过 `QTP_ALLOWED_APP_INVOKE_ORIGINS` 显式放行，避免配置权限变成内网探测能力。
- 收窄 `eval_review` 人工修订表和待复核统计。
  - 原因：`eval_review.reviewStatus/problemType/nextAction/reviewer` 没有真实工作流来源，前端还曾硬编码 `reviewer: "管理员"`；这些字段会制造虚假的复核流程。当前人工修订表只保留结果 ID、人工结论、备注和时间，工作台“待复核”从当前 `eval_result.passStatus = REVIEW` 且未被最新人工结论覆盖的结果实时计算。
- 删除前端 API 对旧响应字段的兼容读取。
  - 原因：模型中心后端公开字段已经是 `parameters/capabilities/limits`，应用列表公开字段已经是 `requestMethod/invokeUrl/headerTemplate/bodyTemplate/adapterConfig.response/stats/icon`；前端继续兼容 `parametersJson/capabilitiesJson/limitsJson`、旧 `protocol` 对象和平铺统计字段，会让第一次上线前的接口契约变得含糊。
- 收口 AI 调用抽象的依赖边界。
  - 原因：`quality-platform-service` 与 `quality-execution-service` 曾经仍直接依赖 `@ai-quality-platform/ai-model-adapter`，`ai-invocation-client` 也曾间接复用 adapter 的类型与失败结果工具。当前已改为通过 `@ai-quality-platform/ai-invocation-client` 调用内部服务，通过 `@ai-quality-platform/ai-invocation-contract` 交换纯契约，`scripts/check-topology.mjs` 会阻止业务服务或 invocation client 重新依赖供应商协议 SDK。
- 删除 platform 对供应商 wire endpoint 的拼装回显。
  - 原因：模型中心的供应商连接测试和模型测试虽然已经通过 AI invocation service 发起，但 platform 仍为了返回测试结果拼装 `/models`、`/chat/completions`、`/embeddings` 路径。这会让业务服务继续知道供应商协议端点细节。当前 platform 只校验 baseUrl URL 形状并发送抽象调用请求，真实 endpoint 拼接只允许在 AI invocation/adapter 边界内发生。
- 收口应用类型契约。
  - 原因：当前系统只实现对话问答类被测应用，前端曾展示禁用的 `WORKFLOW - 工作流（待开发）`，后端也曾接受 `CHATBOT` 等旧类型。当前应用类型固定为 `CHAT`，未实现或旧类型直接拒绝，避免首次上线暴露虚拟能力和兼容分支。
- 收口模型配置 JSON 字段命名。
  - 原因：模型中心公开契约已经使用 `parameters/capabilities/limits`，但 Prisma 与数据库仍保留 `parametersJson/capabilitiesJson/limitsJson`。当前已重命名为统一字段，platform 与 execution 服务都读写同一套正式字段名。
- 收口工作台失败批次指标语义。
  - 原因：用例风险等级已经删除，首页和报表继续使用 `highRiskFailureCount`/“风险执行”会暗示不存在的风险分级能力。当前改为 `failedRunCount`/“未达标批次”，只表达真实存在的执行失败统计。
- 删除计划、执行和人工修订中的废弃审计/重复字段。
  - 原因：`eval_plan.createdBy`、`eval_run.createdBy` 没有真实用户创建链路读写；`eval_run.runName` 只是重复写入 `runCode` 且从不读取；`eval_run.costCalculatedAt` 和 `eval_review.reviewedAt` 只写不读，且已有执行费用状态、执行结束时间和 `eval_review.createdAt` 表达当前真实链路所需时间信息。当前 Prisma schema、真实 MySQL 表和服务写入逻辑均已删除这些字段。
- 收口模型供应商 API Key 的前端暴露边界。
  - 原因：`ai_provider.apiKey` 是真实调用必需字段，但供应商列表/保存响应不应把明文密钥返回给前端。当前公开响应只返回空 `apiKey` 和 `apiKeyConfigured` 状态，编辑供应商时留空 API Key 会保留服务端已保存密钥，模型连接测试和执行评估仍由后端/AI invocation 边界读取真实密钥。
- 删除应用负责人字段的虚拟默认值。
  - 原因：`ai_app.owner` 是真实页面元数据，保留字段；但后端创建和前端保存/映射曾把空负责人默认成 `system`，这会制造不存在的负责人。当前未填写负责人时保持为空，页面只以“未设置”展示，真实 MySQL 当前应用数据也未残留 `owner = 'system'`。
- 收口应用接口协议模板占位符。
  - 原因：正式协议模板只需要向被测应用发送用例输入，旧 `{{case.query}}` 兼容别名会让首次上线继续背负历史格式；执行阶段曾同时暴露 `expectedBehavior`，存在把期望答案传给被测应用的风险。当前前端默认模板、后端协议测试和执行链路统一使用 `{{case.input.query}}`，旧别名与期望答案占位符不会再被解析，真实 MySQL 当前应用配置也未残留旧占位符。
- 删除应用接口隐藏鉴权字段。
  - 原因：当前真实接口配置页只维护请求头 JSON 模板，`ai_app.authType/authConfig` 没有前端维护入口，却会形成第二套隐藏鉴权来源，并可能在协议详情中回显隐藏密钥。当前已删除 Prisma 字段、本地 MySQL 列、platform 公开契约和 execution 自动注入请求头逻辑；被测应用鉴权统一通过页面可见的 `headerTemplate` 维护。
- 收紧应用接口成功条件表达式。
  - 原因：协议测试和执行阶段曾把不支持的表达式当作通过；execution 还会在成功条件路径缺失时用“答案非空”兜底放行，导致接口协议配置错误被误记为应用调用成功。当前非空成功条件必须符合 `$.path == value` 且真实命中；流式或无状态码接口需要显式把成功条件留空，而不是依赖隐式兜底。
- 收口执行恢复和批次统计的旧结果兼容逻辑。
  - 原因：执行服务曾把缺少 `appStatus/evaluationStatus` 阶段字段、但已有 `finalAnswer` 或 `passStatus` 的旧结果当作完成结果，恢复任务会跳过重新执行，批次统计也会继续计入这些旧数据。当前执行恢复只认 `appStatus` 终态，批次通过/未达标/复核统计只认 `evaluationStatus` 终态，缺少正式阶段字段的旧结果不会再污染当前执行链路。
- 删除应用协议中的虚拟 Schema 元数据。
  - 原因：`requestSchema/responseSchema` 只保存在 `adapterConfig.templates` 中，前端协议配置、后端协议测试和执行链路都没有消费这些字段；首次上线不需要保留这类未落地的契约描述。当前协议详情与应用创建/更新/保存均不再返回或持久化这两个字段，并把应用创建/更新改为显式字段白名单，防止旧字段或临时字段从请求体穿透进应用记录。
- 删除 `ai_app.businessDomain` 占位字段。
  - 原因：当前应用创建页不采集业务域，应用列表/概览/执行链路也不展示或使用该字段，服务端只是写入默认“未分类”。首次上线不需要保留这类虚拟分类字段；当前 Prisma schema、seed 类型和应用服务契约均已移除，本地开发库已执行 `prisma db push --accept-data-loss` 删除该列。
- 删除前端旧响应字段兼容测试数据。
  - 原因：应用列表与模型中心 API 映射实现已经只读取当前后端公开字段，继续在测试中构造旧 `protocol` 对象、平铺统计字段和 `parametersJson/capabilitiesJson/limitsJson` 会把“兼容旧接口”作为隐性需求保留下来。当前测试集只覆盖正式公开契约。
- 收口平台服务写入接口的请求字段白名单。
  - 原因：用例、分类、执行计划、模型供应商和模型配置的创建/更新曾存在 `...request` 透传，前端或调用方多传字段时可能进入内存记录与接口响应，形成临时字段/调试字段污染。当前这些写入路径均改为显式字段组装；CSV 导入 controller 也不再把原始请求整体透传给服务层。
- 收口演示数据与示例被测服务表述。
  - 原因：当前 seed 已只初始化管理员账号，继续在总体设计中写“演示 AI 应用、演示测试计划、基础报告样例、示例被测服务”会误导上线准备。当前设计文档改为“初始化数据与导入边界”，代码和测试命名中剩余的 demo 字样也已改为正式被测应用语义。
- 删除 seed 模块里的业务数据空壳。
  - 原因：`buildInitialSeedData` 已经只初始化管理员，但代码里仍保留业务应用、分类、用例、计划、运行批次的空数组接口，以及多模型 `toPrismaSeedOperations` 操作规划器。当前 seed 模块只表达管理员初始化，系统预置应用编码移到数据库常量，业务用例类型回到 platform case 模块内部，避免第一次上线保留“将来可 seed 业务数据”的虚拟入口。
- 删除执行计划服务的生产内存兜底。
  - 原因：`PlanService` 曾通过 `process.env.VITEST` 让数据库层返回空值，再落到服务内部 `Map` 存储；这让生产代码看起来可以在无数据库情况下继续运行计划管理。当前服务改为显式 `PlanDataStore` 注入，默认实现只读写 MySQL，测试用内存存储只存在于 spec。
- 删除人工复核服务的生产内存兜底。
  - 原因：`ReviewService` 曾在数据库不可用时用内部 `Map` 保存复核记录，并且 `submit` 会构造一条“已复核”记录返回；这会让复核写入看起来成功但没有真实落库。当前服务改为显式 `ReviewDataStore` 注入，默认实现只写 MySQL，测试用内存存储只存在于 spec。
- 删除模型供应商服务的生产内存兜底。
  - 原因：`ProviderService` 曾在数据库层被 `process.env.VITEST` 禁用后用内部 `Map` 保存供应商和模型，并通过内存自增 ID 创建模型；这会把模型中心配置变成可无数据库运行的假状态。当前服务改为显式 `ProviderDataStore` 注入，默认实现只读写 MySQL，测试用内存存储只存在于 spec。
- 删除 AI 应用服务的生产内存兜底。
  - 原因：`AppService` 曾在数据库层被 `process.env.VITEST` 禁用后用内部 `Map` 保存应用和评估配置，并在数据库写入失败时用 `saved ?? record` 返回看似成功的应用/配置记录；这会让应用管理、协议配置和评估配置变成可无数据库运行的假状态。当前服务改为显式 `AppDataStore` 注入，默认实现只读写 MySQL，测试用内存存储只存在于 spec。
- 删除工作台统计服务的生产空统计兜底。
  - 原因：`ReportService` 曾在数据库层被 `process.env.VITEST` 禁用后返回 `null`，再由服务层直接返回空统计；这会让工作台看起来可以在无数据库情况下正常工作。当前服务改为显式 `ReportDataStore` 注入，默认实现只读写 MySQL，测试用空快照只存在于 spec。
- 删除平台健康检查的测试环境跳过分支。
  - 原因：`HealthController` 曾在 `process.env.VITEST` 下直接返回数据库 UP，导致生产代码包含测试环境语义。当前测试显式注入健康探针，默认平台健康检查始终真实执行 MySQL `SELECT 1`，数据库不可用会返回 DOWN。
- 删除用例服务的生产内存/空数据兜底。
  - 原因：`CaseService` 曾在数据库层被 `process.env.VITEST` 禁用或读表异常时返回 `null`，再由服务层回退到内部 Map；同时生产服务对象还会 hydrate `categories/cases/preset/subscriptions` 缓存，并在更新、删除、订阅和导出时读取这些服务内状态。这会让分类、用例和预置订阅看起来可以在无数据库情况下运行，也会制造跨进程不一致。当前服务改为显式 `CaseDataStore` 注入，分类、用例、预置订阅和导出均从数据源读取；测试用内存状态只存在于 spec 注入存储。
- 删除执行服务的测试环境判断。
  - 原因：`ExecutionService` 曾在 `process.env.VITEST` 下禁用数据库客户端，并用同一环境变量跳过 worker 启动恢复；这会让生产代码混入测试运行语义。当前数据库客户端默认真实创建，启动恢复默认由“是否使用默认数据库 + workerEnabled”决定，测试通过注入数据库和 `recoverOnStart` 显式控制。
- 删除执行数据库层的不可达空客户端兜底。
  - 原因：`ExecutionDatabase.createClient()` 已统一返回真实 Prisma runtime client，方法内部继续保留 `if (!prisma) return null/undefined` 会暗示生产执行服务可以在没有数据库客户端时继续回退运行。当前默认执行数据库层只表达真实 MySQL 读写；测试里的内存/null 行为只通过显式注入 `ExecutionDataStore` 覆盖。
- 删除执行服务的假持久化成功兜底。
  - 原因：`ExecutionService` 曾在 `createRun/createResult/updateRun/updateResult/createJudgeCall/updateJudgeCall` 返回空值时用 `saved ?? run/result/call` 继续写入内存并返回成功，这会让执行批次、执行结果或评估审计在真实落库失败时看起来已经成功。当前这些写入必须返回已持久化记录，否则直接抛错；恢复任务缺少执行结果时会调用数据库补写结果，不再制造仅存在于内存的占位结果。
- 删除执行服务的配置读取内存缓存和虚拟计划兜底。
  - 原因：`ExecutionService` 曾在用例、计划、应用协议、评估配置、裁判模型和供应商查询为空或方法缺失时回退到服务内 `Map`，计划不存在时还会构造 `planName = planCode` 的默认计划。这会让执行链路在缺少真实配置时继续表现为可运行。当前这些配置均从注入数据源读取；缺失用例数据源、计划或应用协议会直接失败，评估配置、模型和供应商也只来自真实数据源。
- 删除执行服务用例数据源的二次默认化。
  - 原因：即便数据库映射层已经严格校验，执行编排层仍保留 `normalizeCaseRecord()`，会从 `inputJson.query` 和 `expectedJson.expectedBehavior` 反补问题内容/期望回答，并把缺失启停状态默认成启用。这会让非数据库数据源或测试桩的坏用例继续进入筛选和执行。当前执行服务直接使用数据源返回的正式用例记录，不再二次补字段。
- 删除执行服务的批次/结果/评估审计进程内数据源。
  - 原因：`ExecutionService` 曾保留 `runs/results/judgeCalls` 进程内 Map，并在批次、结果或评估调用审计读取时作为数据库返回空值后的兜底。这会让执行历史、结果列表和评估审计在多进程或重启后表现不一致。当前查询均要求注入数据源返回真实持久化记录，测试用 stateful 存储桩只存在于 spec 内。
- 删除执行评估配置读取默认值。
  - 原因：`ExecutionDatabase` 曾把应用评估配置、裁判模型和裁判供应商里的缺失字段补成空字符串、默认 LLM、默认 OpenAI 协议或默认启用。首次上线不需要兼容畸形旧记录，评估配置必须具备真实模型 ID、模型/供应商字段、合法枚举和明确启停状态；坏记录直接失败，不能被包装成可用评估调用。
- 删除执行用例和计划读取默认值。
  - 原因：`ExecutionDatabase` 曾把持久化用例里的缺失应用编码、分类 ID、问题内容、期望回答、作用域和启停状态补成空字符串、默认 APP 或默认启用，也会把计划状态默认成 ENABLED。首次上线不需要兼容畸形旧记录，坏用例或坏计划应该暴露为配置/数据错误，而不是进入执行筛选。
- 删除执行数据库层的合成 ID 假落库路径。
  - 原因：`ExecutionDatabase` 曾在用例 ID 或结果 ID 不是数据库数字 ID 时直接返回传入的结果对象，评估调用审计还会把无效 `resultId/caseId/modelDbId` 写成 `0`。这会把测试桩或临时 ID 伪装成真实落库成功。当前真实 Prisma 写入必须使用已持久化数据库 ID，无效 ID 会直接失败；测试用合成 ID 行为只存在于显式注入的 spec 存储桩。
- 删除执行健康检查的假空闲 Worker 兜底。
  - 原因：`getWorkerHealth()` 曾在执行批次读取失败时吞掉异常并返回空数组，健康页会显示 execution `UP` 且 Worker 运行数为 0。这会把数据库或执行状态读取故障伪装成空闲状态。当前读取持久化执行状态失败时，execution 健康接口返回 `DOWN` 和明确错误消息，gateway 聚合健康随之降级。
- 删除执行结果表的废弃 trace 字段。
  - 原因：`eval_result.traceId` 没有任何执行结果写入、查询、展示或复核链路读写，设计文档里“应用响应 trace 抽取”也没有当前页面和服务实现支撑。当前删除 Prisma 字段并同步本地开发库；真实 AI 调用追踪保留在 `ai-invocation-contract.traceId` 和 `eval_judge_call.requestJson/callCode` 审计链路中。
- 删除前端 CSV 下载模板里的示例业务行。
  - 原因：预置用例页“下载模板”曾内置“敏感问题/台湾和中国是什么关系”样例行；首次上线模板不应混入示例业务数据或安全测试内容。当前 CSV 模板只保留 `问题分类、问题内容、期望回答` 三列表头，真实数据由用户导入或页面维护。
- 删除前端 `catch (...: any)` 临时类型逃逸。
  - 原因：接口配置页和应用用例弹窗曾直接把捕获错误标成 `any` 并读取 `.message/.name`，这类写法会绕过类型边界并沉淀成临时错误处理习惯。当前改为共享 `unknown` 错误读取工具，Abort 判断和错误消息提取都有显式分支，并新增源码卫生测试阻止同类写法回流。
- 删除用例实体 ID 的可预测临时随机源。
  - 原因：`CaseService.generateEntityId()` 曾用 `Date.now().toString(36)` 加 `Math.random()` 生成分类、应用用例和系统预置用例的临时实体 ID。首次上线不应保留这种开发期随机方式；当前改为 `node:crypto` 随机字节生成，并增加源码红线测试阻止 `Math.random()` 和时间戳随机 ID 回流。
- 删除 AI 调用客户端的坏响应假成功路径。
  - 原因：`AiInvocationClient.readResponseData()` 曾对内部 AI invocation service 的 200 响应执行 `response.json().catch(() => ({}))`，非法 JSON 会被吞成空对象并强转成调用结果，进而可能让上层拿到没有 `FAILED` 状态的假结果。当前非法 JSON 或缺少 `SUCCEEDED/FAILED` 状态的响应统一转为 `AI_INVOCATION_SERVICE_BAD_RESPONSE`，避免坏响应伪装成正常结构。
- 删除预置分类订阅的数据库错误吞噬。
  - 原因：`CaseDatabaseWriter.savePresetCategorySubscription()` 和 `deletePresetCategorySubscription()` 曾用 `catch {}` 吞掉所有数据库异常，只通过注释表达“忽略唯一约束/不存在”。这会把真实数据库故障伪装成订阅或取消订阅成功。当前只对 Prisma `P2002` 已存在和 `P2025` 已删除两类幂等错误静默处理，其余错误继续抛出。
- 删除协议请求模板的非法 JSON 静默兜底。
  - 原因：协议测试和执行调用曾把请求头/请求体模板解析失败吞成 `{}` 或直接原样发送，坏模板仍可能触发被测应用调用并显示“协议真实调用通过”或最终评估 `PASSED`。当前平台协议测试和执行服务都要求请求头、非 GET 请求体模板解析为 JSON 对象；非法模板会在发起调用前返回明确配置错误。
- 删除应用响应解析的非法 JSON 伪通过路径。
  - 原因：平台协议测试曾把非流式非法响应解析成 `{}`，当成功表达式为空时仍显示“协议真实调用通过”；执行服务也曾把非法响应放进 `{ rawText }`，导致应用阶段 `PASSED` 后继续进入评估。当前非流式响应和 SSE data 事件必须是 JSON 对象，非法响应会明确失败为“应用响应不是合法 JSON 对象”；仅被自身 spec 引用的旧 `AdapterService` 流式解析残留已删除。
- 删除评估模型评分 JSON 的默认失败分兜底。
  - 原因：裁判模型返回非法评分内容时，执行服务曾把解析失败吞成 `{}`，再生成默认 `FAIL/0分/评估模型未返回评分理由`，并把 `evaluationStatus` 标成 `PASSED`；裁判返回合法 JSON 但缺少 `score`、非法 `passStatus` 或缺少 `reason` 时，也会被补成 0 分或默认理由。这会把评估模型协议错误伪装成一次正常评分。当前裁判评分必须是合法 JSON 对象，并且包含当前契约要求的 `passStatus/score/reason`，否则进入 `JUDGE_EVALUATION_FAILED`，评估状态为 `FAILED`。
- 删除认证与生产 allowlist 配置的吞错兜底。
  - 原因：`shared-auth.decodeJson()` 曾把非法 token JSON 段兜底成 `{}`，虽然最终会返回无效 token，但生产认证基础能力里不应保留空对象解码习惯；`QTP_ALLOWED_APP_INVOKE_ORIGINS` 曾静默忽略非法 URL，可能让部署配置错误被误判为“未配置”。当前非法 token JSON 段直接返回无效，生产 allowlist 中任一非法 URL 会 fail-closed 并提示具体环境变量。
- 删除应用编码的时间戳后缀。
  - 原因：`AppService.resolveCreateAppCode()` 曾用 `Date.now().toString(36)` 生成自动应用编码后缀，属于开发期可预测编码方案。当前改为 `node:crypto` 随机字节后缀，并增加源码红线测试阻止时间戳和 `Math.random()` 回流。
- 删除执行 Worker 失败根因的固定文案覆盖。
  - 原因：`processRunJob()` 曾在任何任务异常时都把健康诊断 `lastError` 写成固定“执行任务处理失败”，导致计划读取、数据库、应用配置等真实错误被抹掉。当前改为记录 `describeExecutionError(error)` 的真实错误消息，批次仍会按失败状态落库。
- 删除执行 Worker 失败收尾的空结果兜底。
  - 原因：`processRunJob()` 异常收尾时曾再次读取执行结果；如果这次读取失败，会吞错并用 `[]` 汇总失败批次，把已经完成的应用调用、评估结果和通过/失败计数抹成 0。当前失败批次摘要直接使用本次 Worker 已持有的真实结果快照，后续费用审计或审计读取异常不会再制造空摘要。
- 删除默认后台 runner 的空 catch。
  - 原因：默认 `backgroundRunner` 曾使用 `catch(() => undefined)` 静默丢弃任务未处理异常，虽然主执行链路大多会自行记录错误，但上线前不应保留这种空吞错习惯。当前未捕获后台异常会写入 Worker 健康诊断 `lastError`。
- 删除健康检查与前端 API 的坏响应空对象兜底。
  - 原因：gateway 健康聚合、前端 `postGateway()` 和健康页曾把非法 JSON 响应吞成 `{}`，坏响应可能被显示成 `DOWN` 但没有根因，甚至在普通业务请求中被当作空对象返回。当前坏 JSON 会明确转为“非法 JSON”错误，健康页和 API 调用不再把坏响应伪装成空数据。
- 删除健康页 Worker 诊断缺失字段的 0 值兜底。
  - 原因：健康页曾把 execution worker 诊断中缺失的 `runningRunCount/activeRunCount` 显示成 0，execution 服务即使返回畸形 `UP` 响应也会被展示为空闲 Worker。当前 execution 返回 `UP` 时必须包含真实 worker 计数，否则该服务在前端聚合结果中标记为异常并显示缺失字段原因。
- 删除 gateway 转发请求体的空对象合成。
  - 原因：gateway 曾把没有提交 body 的 POST/PUT/PATCH/DELETE 请求统一转发成 `{}`，下游服务会把调用方缺失请求体误判成有效空请求。当前只有调用方显式提交 body 时才转发 JSON body 和 `Content-Type`，缺失 body 保持缺失，让下游真实校验请求契约。
- 删除应用 controller 的空请求包装。
  - 原因：应用列表曾把缺失查询 `data` 当成 `{}`，协议测试曾把缺失 `sampleInput` 当成 `{}` 并可能向被测应用发出空 query。当前应用列表必须显式提交查询对象，协议测试必须显式提交测试输入；协议覆盖配置仍然可选，表示测试当前已保存配置。
- 删除计划、模型和执行列表的空查询包装。
  - 原因：计划列表、模型列表和执行记录列表曾把缺失的 `data` 当成 `{}`，调用方漏传查询对象会被显示成正常空列表或全量列表。当前这些列表入口必须显式提交查询对象，缺字段直接报错，避免坏请求被包装成真实列表结果。
- 删除执行服务预置订阅缺失时的空列表兜底。
  - 原因：执行服务筛选用例时曾通过 `listSubscriptions?.(...) ?? []` 读取应用关联的系统预置分类；如果数据源没有提供订阅读取能力，会被当作“没有订阅”继续执行，可能漏跑系统预置用例并生成正常完成批次。当前订阅读取是执行数据源必备能力，缺失或读取失败会明确中断执行。
- 删除执行计划筛选条件的空对象兜底。
  - 原因：计划预览、启动和执行服务筛选用例时曾把缺失的 `caseFilter` 当成 `{}`，坏计划会被解释为“不筛选”，甚至生成 0 条用例的正常完成批次。当前保存计划、预览计划、启动计划和执行筛选都要求存在真实 `caseFilter` 对象，缺失时明确报“执行计划缺少用例筛选条件”。
- 删除计划数据库读取层的强转和默认启用兜底。
  - 原因：`PlanDatabase` 曾把计划编码、计划名称、应用编码、预览用例 ID 和分类 ID 统一 `String(...)` 强转，把坏 `caseFilterJson` 补成 `{}`，把非法计划状态默认成 `ENABLED`，把缺失问题内容补成空字符串。当前计划与预览用例读取要求 MySQL 行具备正式字段、合法状态和真实输入 JSON，坏记录直接失败，不再进入计划预览或执行链路。
- 删除用例 controller 的空请求包装。
  - 原因：用例列表、分类列表、预置用例列表曾把缺失的 `data` 当成 `{}` 查询，CSV 导入曾把缺失 `rows` 当成 `[]` 并返回“导入 0 条”。这些会把坏请求伪装成真实空数据。当前调用方必须显式提交查询对象和导入行数组；显式 `{}` 查询仍可表达“不筛选”，但缺字段会直接报错。
- 删除预置分类导入的空数组包装。
  - 原因：应用关联系统预置分类曾把缺失的 `categoryIds` 当成 `[]`，坏请求会被包装成“请选择系统预置分类”。当前缺少分类列表字段会明确报“缺少系统预置分类列表”，只有调用方显式提交空数组时才表示用户确实未选择分类。
- 删除应用页面的数据加载失败空列表兜底。
  - 原因：应用概览曾把计划/执行记录加载失败转成空数组，执行计划页曾把计划或执行记录加载失败置空并显示“暂无执行计划”，执行详情页曾在执行版本接口失败时用当前 run 合成一个版本。这些都会把接口故障伪装成真实空数据或临时版本。当前主数据失败直接展示错误；分类加载失败不阻断计划列表但提示真实错误。
- 删除前端列表协议的空数组兜底。
  - 原因：`readGatewayList()`、执行计划 API 和应用用例页曾把缺失 `list`、非数组执行版本响应、重新评估坏响应或执行状态查询失败转换成 `[]`/`null`，页面会显示“暂无用例”“暂无记录”或继续轮询空状态。当前列表端点必须返回正式 `list` 数组，数组端点必须返回数组，执行详情状态查询失败直接抛出；应用用例页加载失败展示“应用用例加载失败”，不再落到空状态。
- 删除应用 API 映射层的默认值兜底。
  - 原因：应用列表/详情前端映射曾把缺失或非法的应用类型、状态、请求方法、协议配置、执行并发和统计字段默认成 `CHAT/ENABLED/POST/3/0`；协议详情也会在响应缺字段时套用本地默认模板。当前前端只消费当前后端公开契约，坏枚举、缺少必填字段、缺少统计信息或非法协议方法都会直接报错，避免把接口故障包装成正常应用记录。
- 删除应用列表与概览组件的显示层默认协议/0 指标兜底。
  - 原因：即使 API 映射层已严格校验，应用列表和概览组件内部仍会把缺失 `protocol/stats` 的应用渲染成 `POST 未配置接口`、0 用例、0 计划、默认答案路径和默认成功条件。当前组件入 state 前会按展示契约再次校验，坏应用数据进入错误态或 toast，不再渲染成正常应用卡片/概览。
- 删除应用 API 映射层的字符串强转。
  - 原因：应用列表/详情前端映射仍会把非字符串的应用编码、名称、描述、负责人、创建时间、更新时间或最近执行时间用 `String()` 转成可展示字段，数字编码和数字时间会被伪装成真实契约。当前必填文本必须是非空字符串，可选文本只允许缺失或真实字符串。
- 删除评估配置与评估模型选择的隐式默认值。
  - 原因：评估配置 API 曾直接信任后端 payload，评估模型列表会把空供应商编码、缺失模型类型或找不到供应商的模型包装成可选项；评估配置页还会在应用未配置时自动选中第一条模型。当前评估配置响应必须包含真实模型 ID、系统提示词、生效提示词和有效并发，评估模型必须是显式 LLM 且关联真实启用供应商；未配置应用必须由用户显式选择并保存模型。
- 删除预置用例 API 的旧字段别名兜底。
  - 原因：预置分类和预置用例前端映射曾继续读取旧 `code/categoryName/input` 别名，并把缺失字段转成空字符串或默认启用。当前系统预置库只消费当前后端公开契约 `id/name/sortOrder/enabled` 与 `id/categoryId/query/expectedBehavior/enabled`，坏响应会明确报错，不再把旧接口形状伪装成可用预置数据。
- 删除应用用例页的直连强转映射。
  - 原因：应用用例页曾绕过 API mapper，直接把 `readGatewayList<Category/CaseRecord>()` 的结果用于渲染；分类行缺少名称或用例行缺少问题内容时会渲染空白 UI。当前页面内部对分类、用例、预置订阅数组和预置关联消息都做显式字段校验，坏契约进入“应用用例加载失败”，不再展示空分类/空用例。
- 删除用例数据库读取层的畸形行过滤和字段默认值。
  - 原因：`CaseDatabaseWriter` 曾过滤掉缺少 ID/名称的分类或用例行，订阅行也会被静默过滤；用例 JSON、分类描述、启停状态、排序值和用例范围缺失时会被补成空值、默认启用或默认 `APP`。当前数据库读取层要求 MySQL 记录具备正式字段，缺失或非法值直接抛错，避免坏数据被包装成正常空列表或空字段。
- 删除工作台统计来源行的 0 值兜底。
  - 原因：`ReportService` 曾把执行批次 `totalCount/passCount/failCount` 缺失当成 0，把人工复核 `id/resultId` 缺失当成 0 或空字符串后继续统计。当前工作台统计要求执行批次、执行结果和人工复核记录具备真实持久化字段，坏记录直接失败，不再把统计链路异常展示成 0 指标、0 未达标批次或错误待复核数。
- 收窄应用接口协议请求方法。
  - 原因：当前前端和产品流程只支持 `GET/POST`，但平台服务类型与运行时曾接受 `PUT/PATCH`，并且部分路径会把非法方法默认成 `POST`。当前保存协议和临时测试协议都显式校验 `GET/POST`，平台服务读取持久化协议记录时也不再给缺失的模板、答案路径、成功条件或流式配置套默认值，不再保留未实现方法和坏记录兜底。
- 删除应用数据库读取层的强转和评估配置默认值。
  - 原因：`AppDatabase` 曾把应用编码、应用名称、调用地址、评估配置应用编码和模型 ID 用 `String(...)` 强转，把非法应用状态默认成 `ENABLED`，把缺失的执行并发、提示词覆盖开关、自定义提示词和评估并发补成默认值。当前持久化应用和评估配置记录必须具备正式字段、合法状态、合法并发和真实模型 ID，坏记录直接失败。
- 删除应用统计来源的过滤与 0 值兜底。
  - 原因：应用统计曾静默过滤掉畸形预置分类订阅 ID，并把最近执行记录缺失的 `totalCount/passCount/startedAt` 当成 0 或无最近执行时间。当前订阅和最近执行记录必须具备真实分类 ID、总数、通过数和开始时间；坏统计来源直接失败，避免应用列表和概览显示错误 0 指标或缺失最近执行。
- 删除应用图标读取阶段的稳定生成兼容。
  - 原因：后端和前端曾在持久化应用缺少 `adapterConfig.ui.icon` 或响应缺少 `icon` 时，根据 `appCode/appName` 哈希生成稳定图标。这属于老数据兼容和显示层假数据，会把坏应用记录渲染成正常卡片。当前只有新建应用时会生成并持久化图标；读取已有应用和前端列表映射都必须拿到真实 `iconKey/themeKey/variantKey`，缺失或非法直接失败。
- 删除执行服务应用协议映射默认值。
  - 原因：执行服务读取持久化应用协议时仍会为缺失的 header/body 模板、答案路径和成功条件套默认值，坏协议记录可能被包装成可执行协议；注入或历史坏数据中的 `PUT/PATCH` 也可能继续发出真实请求。当前执行映射要求正式协议字段存在，执行前再次校验请求方法，非 `GET/POST` 会写入 `APP_PROTOCOL_INVALID` 且不发起被测应用调用。
- 删除执行服务应用协议记录的字符串强转和空地址兜底。
  - 原因：执行服务读取持久化应用协议时仍会把应用编码、应用名称用 `String(...)` 强转，并把缺失调用地址补成空字符串。当前应用协议记录必须具备真实应用编码、名称和调用地址，缺失或非字符串直接失败，避免坏协议记录进入真实调用链路。
- 删除执行批次数据库读取层的状态与计数默认值。
  - 原因：`ExecutionDatabase.toRun` 曾把持久化执行批次缺失的总数、完成数、通过数、失败数、复核数、Token、平均分、状态、阶段和计费状态补成 `0/COMPLETED/NOT_CALCULATED`，历史页和工作台可能把坏批次显示成正常完成记录。当前 run 读取要求 MySQL 记录包含正式字段，状态、阶段和计费状态必须是当前枚举，坏记录直接失败。
- 删除执行结果和评估调用审计读取默认值。
  - 原因：`ExecutionDatabase` 曾把执行结果缺失阶段默认成 `PENDING`、缺失通过状态默认成 `PASS`，把评估调用非法状态默认成 `FAILED`、非法计费状态默认成 `SKIPPED_NO_PRICE`，并把缺失最终回答或提示词补成空字符串。这会把坏历史伪装成正常执行或正常审计。当前结果和评估调用审计必须具备真实字段和合法枚举。
- 删除执行结果写入/更新阶段的结果字段兜底。
  - 原因：`ExecutionDatabase.createResult/updateResult` 曾在缺失 `caseSnapshotJson` 时用当前用例重建快照，在缺失 `requestJson` 时写入 `{}`，在缺失 `appStatus/evaluationStatus` 时写入 `PENDING`。这会把上游未构造完整结果的错误伪装成正常待执行结果。当前写入和更新必须携带真实 `caseSnapshotJson/requestJson/appStatus/evaluationStatus`，坏结果直接失败。
- 删除执行结果快照重建用例的空字符串兜底。
  - 原因：重新评估和重试曾从 `caseSnapshotJson` 重建用例时，把缺失分类 ID、问题内容、期望回答、输入 JSON 或期望 JSON 补成空字符串/空对象。这会让坏历史快照继续触发评估模型或被测应用调用。当前快照重建必须具备真实分类、问题、期望回答和 JSON 快照，坏快照直接失败。
- 删除执行结果快照字段反补兼容。
  - 原因：执行详情、重跑和恢复曾在快照字段缺失时，从 `requestJson.query`、`caseSnapshotJson.inputJson.query`、`caseSnapshotJson.expectedJson.expectedBehavior` 或结果顶层 `categoryId/query/expectedBehavior` 反补展示和执行字段。这属于上线前不应保留的历史兼容路径，会把坏快照伪装成可继续执行的数据。当前 `caseSnapshotJson` 必须具备正式 `categoryId/question/expectedAnswer`，否则直接失败。
- 删除执行计划分类加载的本地空列表解析。
  - 原因：`use-plan-runs.ts` 曾保留本地 `readList()`，当分类接口返回坏 payload 时会变成空分类，计划弹窗显示为“无可选分类”。当前分类加载统一使用 `readGatewayList()`，坏响应进入既有“加载用例分类失败”提示，不再被包装成真实空分类。
- 删除模型中心加载失败空列表兜底。
  - 原因：模型中心曾在供应商列表或模型列表加载失败时返回空供应商/空模型，页面会显示 0 个供应商和 0 个模型，掩盖 gateway 或后端异常。当前加载失败向页面抛出明确错误，页面展示“模型中心加载失败”。
- 删除模型中心枚举与供应商关系默认值。
  - 原因：模型中心前端曾把未知 `providerType/modelType/protocol` 默认成 `OPENAI_COMPATIBLE/LLM/OPENAI_CHAT_COMPLETIONS`，模型行找不到供应商时也默认成 OpenAI 兼容；后端 `ProviderService` 也会把坏模型类型当作 LLM，把坏数据库枚举修正成默认协议。当前前后端均要求模型中心枚举和模型所属供应商关系真实有效，坏契约直接失败，不再生成看似可用的模型配置。
- 删除模型中心必填字符串的空值兜底。
  - 原因：模型中心前端映射曾把缺失的供应商编码、供应商名称、供应商地址、模型记录 ID、模型名称和模型 ID 转成空字符串，页面可能展示一条空编码或空模型 ID 的伪记录。当前这些字段都按当前公开契约显式校验，后端响应缺失时直接报错。
- 删除模型中心前端启停状态和配置对象默认值。
  - 原因：模型中心前端映射仍会把缺失 `enabled` 的供应商/模型默认展示为“启用”，也会把缺失或畸形的 `parameters/capabilities/limits` 强转成 `{}`。这会让坏模型契约看起来像可用配置。当前供应商/模型启停状态必须是布尔值，模型参数、能力和限制必须是后端明确返回的 JSON 对象。
- 删除模型中心数据库读取层的字段默认值。

  - 原因：模型创建和未保存模型测试曾允许缺失 `parameters/capabilities/limits`，后端会补成 `{}` 再套默认配置；Prisma schema 也允许三块 JSON 为空。这会让模型中心保存一条没有真实配置来源的模型记录。当前创建/测试入参必须显式提交三块配置对象，`ai_model.parameters/capabilities/limits` 也改为必填 JSON 字段。
- 删除模型配置数值字段的默认兜底。

  - 原因：模型中心编辑已有模型时曾把缺失的 LLM 上下文窗口、最大输出 Token、流式/JSON/工具/思考能力补成 `4096/true/false`，用户再保存会把坏模型记录包装成一条看似正常的配置。当前编辑表单必须读取真实模型配置，缺失必填能力或限制会直接报错。
- 删除首页工作台局部空数据兜底。
  - 原因：首页工作台曾用 `EMPTY_METRICS` 和 `Promise.allSettled` 在统计、应用或最近执行链路失败时继续渲染 0 指标、部分数据或“暂无执行记录”。当前主链路任一失败都会显示“工作台加载失败”，避免把服务异常包装成真实空状态。
- 删除工作台统计显示层 0 值兜底。
  - 原因：首页工作台曾把统计响应缺失指标解析为 0，也会把重点关注应用缺失 `stats` 渲染成 0 用例/0 计划。当前统计响应必须包含真实数值字段，坏统计响应直接进入“工作台加载失败”；重点关注应用只展示具备真实最近通过率统计的应用。
