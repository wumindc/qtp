# 执行详情语义与历史快照修复实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修正执行详情页的结果语义、人工修订入口、计费摘要样式，并保证执行历史展示的是执行时固化的用例快照，不再受后续用例编辑影响。

**Architecture:** 前端只负责展示和触发人工修订/重试，结果分类以“评估通过、未达标、执行失败”为主，不再把待复核作为独立类别。后端以 `eval_result.caseSnapshotJson` 作为历史日志的事实来源，`eval_review` 只记录人工覆盖结果，不反向修改原始执行记录。

**Tech Stack:** Next.js + React + shadcn/ui + lucide-react，NestJS 微服务，Prisma 7 + MySQL，Vitest。

## 需求确认

### 用户反馈

1. 未计费时，“未计算”不需要显示，当前在窄宽度下会把计费摘要挤变形。
2. 亮色模式下统计摘要和结果列表的层次不明显，不像暗色模式那样能看出块与块的间隔。
3. “未达标”不是任务异常，不应该使用打叉图标；列表中的“评估结论”前也不需要再放图标。
4. 不应该有“待复核”这个筛选类别，执行详情只需要区分评估通过、未达标、执行失败。
5. 人工修改评估结果不应该藏在“查看明细”抽屉里，列表中就应该可以修改。
6. 执行详情里的问题内容和期望回答必须是执行当时的固化历史日志；修改预置用例或应用用例后，历史详情不应该跟着变化。

- 补充测试与 `CHANGELOG.md`。

### 不在本次范围

- 不调整执行计划两阶段 worker 架构。
- 不调整模型费用计算规则。

- 不把历史快照拆成新表；优先复用现有 `eval_result.caseSnapshotJson`。

## 当前问题定位

### 1. 历史快照被当前用例覆盖

`packages/shared-database/prisma/schema.prisma` 已有字段：

```prisma
model EvalResult {
  caseSnapshotJson Json?
}
```

`apps/quality-execution-service/src/execution.service.ts` 创建结果时也会写入快照：

```ts
caseSnapshotJson: result.caseSnapshotJson ?? this.caseSnapshot(testCase)
```

但服务返回结果时，当前逻辑仍会用最新用例对象补齐：

```ts
private enrichResult(result: ResultRecord, testCase?: ExecutionCaseRecord): ResultRecord {
  if (!testCase) return result;
  return {
    ...result,
    caseName: result.caseName ?? testCase.caseName,
    query: result.query ?? testCase.query,
    expectedBehavior: result.expectedBehavior ?? testCase.expectedBehavior,
  };
}
```

因此只要历史结果自身没有解析出 `query/expectedBehavior`，页面就会展示当前用例表的值。这是用户观察到“修改预置用例后，历史详情里的期望回答也变了”的直接原因。

### 2. 前端结果语义混杂

当前前端存在 `ResultFilter = 'ALL' | 'PASS' | 'FAIL' | 'EXECUTION_FAILED' | 'REVIEW'`，并展示“待复核”。但本业务页更适合三类结果：

- 评估通过：接口执行成功，AI 裁判判断符合期望。
- 未达标：接口执行成功，但回答不符合期望。
- 执行失败：接口调用报错、协议未配置、目标服务失败、返回为空导致无法评估。

人工修订是覆盖标识，不是新的结果类别。

### 3. 视觉层次在亮色模式不足

暗色模式下底部 token/费用条天然有对比，亮色模式下 `bg-card` 与页面背景接近，统计摘要像一条普通文字。需要为亮色模式提供更明确的背景、边界和分隔。

## 目标交互设计

### 结果筛选

执行详情页筛选项调整为：

- `全部 (n)`
- `评估通过 (n)`
- `未达标 (n)`
- `执行失败 (n)`

移除：

- `待复核`

如果后端返回历史 `passStatus = REVIEW`：

- 不再单独建筛选项。
- 在列表中显示为“未确认”或“未达标待确认”需要产品二选一；本计划建议先归入“未达标”，避免出现第四类结果。
- 人工修订后按人工结果重新归类到“评估通过”或“未达标”。

### 图标语义

| 状态 | 图标建议 | 颜色 | 说明 |
| --- | --- | --- | --- |
| 评估通过 | `CheckCircle2` | 绿色 | 明确达标 |
| 未达标 | `CircleAlert` 或 `AlertTriangle` | 红色或琥珀色 | 不使用 `XCircle`，避免像任务异常 |
| 执行失败 | `AlertCircle` | 红色 | 表示接口执行或协议调用失败 |
| 人工修订 | `PencilLine` 小徽标 | 琥珀色 | 覆盖原始 AI 裁判结果 |

列表中的“评估结论：”前不再放状态图标，只保留文字和颜色。行首状态图标和状态徽标已经足够。

### 人工修订入口

列表行右侧新增轻量操作：

- `修订结果` 下拉菜单。
- 菜单项：
  - `标为评估通过`
  - `标为未达标`
  - `恢复 AI 评估`

规则：

- 人工修订入口出现在评估通过和未达标结果上。
- 执行失败结果优先展示 `重试`，不展示人工修订入口。
- 修订后列表立即更新统计，并在该行状态旁展示 `人工修订` 标识。
- 明细抽屉仍可展示人工修订状态，但不再作为唯一修改入口。

### 计费摘要

底部 token/费用条仍保留：

- 普通输入
- 缓存命中
- 输出
- 费用
- 计费

显示规则：

| costStatus | 费用显示 | 计费项显示 |
| --- | --- | --- |
| `CALCULATED` | `0.03 CNY` | `已计费` |
| `NOT_CALCULATED` | `未计费` | 不显示“未计算”文字，只保留重算按钮 |
| `NO_USAGE` | `未计费` | 不显示“无 usage”文字，只保留重算按钮 |
| `SKIPPED_NO_PRICE` | `未计费` | `未配置价格` |
| `PARTIAL` | 已算出的金额 | `部分计费` |

`NOT_CALCULATED` 和 `NO_USAGE` 这两种状态不再挤出“未计算/无 usage”文案，重算按钮使用 `aria-label="重新计算费用"` 和 tooltip。

### 亮色模式样式

执行详情摘要区域采用更明确的层次：

- 外层摘要卡片：`bg-card border shadow-sm`。
- 顶部四个核心指标：`bg-muted/40 dark:bg-muted/20`，保留圆角。
- 底部 token/费用条：改为 `grid` 中的独立小块，每块 `border bg-muted/35 dark:bg-muted/20`。
- 费用条与顶部指标之间保留分割线 `border-t`。
- 列表容器亮色模式增加 `bg-card`、行 hover `bg-muted/40`，并让单行边界更清晰。

## 后端与 DB 设计

### 历史快照读取

`EvalResult.caseSnapshotJson` 是历史详情的问题内容、期望回答、用例名称的优先来源。

读取优先级：

1. `eval_result.caseSnapshotJson.question`
2. `eval_result.caseSnapshotJson.inputJson.query`
3. `eval_result.requestJson.query`
4. 空值展示 `历史快照缺失`

期望回答读取优先级：

1. `eval_result.caseSnapshotJson.expectedAnswer`
2. `eval_result.caseSnapshotJson.expectedJson.expectedBehavior`
3. 空值展示 `历史快照缺失`

不再使用当前用例表的 `query`、`expectedBehavior` 回填历史结果。

### 写入快照

执行开始创建占位结果时继续写入：

```ts
caseSnapshotJson: {
  caseId,
  caseName,
  categoryId,
  question,
  expectedAnswer,
  inputJson,
  expectedJson,
}
```

执行过程中更新 `eval_result` 时，必须保留已有快照：

- 如果 `result.caseSnapshotJson` 已存在，原样保存。
- 不因为当前用例被编辑而刷新历史快照。

### 历史数据兼容

对已有 `caseSnapshotJson = null` 的旧记录：

- 本次不自动用当前用例回填，避免把错误的“当前值”写成历史事实。
- 页面展示 `历史快照缺失`。
- 如确实需要修旧数据，另起一次数据修复任务，根据 `requestJson` 和 `eval_judge_call.requestJson` 尽量恢复。

### DB 变更

本次不新增字段。原因：

- `eval_result.caseSnapshotJson` 已经存在。
- `eval_review.manualResult` 已能表达人工覆盖结果。

需要检查本地 DB 是否已同步字段：

```bash
pnpm db:push
```

如果某个环境缺少 `caseSnapshotJson`，通过 Prisma push 补齐，不写手工 SQL。

## 验收标准

1. 修改预置用例或应用用例后，历史执行详情的问题内容和期望回答不变化。
2. 执行详情页只显示 `全部 / 评估通过 / 未达标 / 执行失败` 四个筛选项。
3. 未达标不使用打叉图标，评估结论文字前不重复放图标。
4. 列表行可以直接人工修订结果，并显示人工修订标识。
5. 执行失败结果可以单条重试，评估未达标结果不显示重试。
6. 未计费时不展示 `未计算` 三个字；重算能力仍可用。
7. 亮色和暗色模式下，统计摘要、费用条、列表卡片都有清晰层次。
8. 全量测试、类型检查、健康检查通过。

## 风险与处理

| 风险 | 处理 |
| --- | --- |
| 旧历史记录没有 `caseSnapshotJson` | 不再错误回填当前用例，展示快照缺失；如需要修旧数据，另起数据修复任务 |
